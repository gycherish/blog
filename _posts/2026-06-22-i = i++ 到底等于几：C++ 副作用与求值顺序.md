## 一行说不清的代码

先看这段代码：

```cpp
int i = 0;
i = i++;
```

`i` 最后是 0 还是 1？

再看一段代码，两个 `i++` 到底先算哪个：

```cpp
f(i++, i++);
```

这两行都没有线程、没有并发，答案却不好说。它们看着是在考 `++` 操作符，而真正问的是：一个表达式里，这些动作到底谁先谁后？

## as-if 规则

要回答“谁先谁后”，得先弄清编译器和 CPU 到底向你承诺了什么。

它们不承诺按你写的顺序来一条条执行你的代码。在标准眼里，你的源码是一份“结果说明书”：它规定程序该产生什么效果，至于用什么步骤、什么顺序达到，是实现自己的事。

这份自由正是性能的来源。为了跑得快，编译器会：

- 把变量留在寄存器里
- 删掉算了也没人要的表达式
- 调换指令顺序
- 把几次写合并成一次
- ...

此外，真实硬件上底层执行的顺序也可能和源码不同。只要最后的效果对得上，这些都合法。

标准把这条底线叫 `as-if` 规则。它的意思是，一个符合标准的实现，只需要让程序表现得“就像”它在一台理想的“抽象机”上逐条执行了你的代码一样：

> *conforming implementations are required to emulate (only) the observable behavior of the abstract machine [...]*

这里的“抽象机”是标准用来描述程序语义的一台假想机器；真实实现不必真照它一步步走，只要对外看起来一样就行。

as-if 是几乎所有优化的地基。但它也留下一个问题：“对外看起来一样”里的“对外”到底指什么？

## 副作用：程序真正在“做”的事

在 C++ 里，一个表达式会被[求值（evaluation）](https://eel.is/c++draft/intro.execution#7)，一次求值可以包含两类动作：

> *Evaluation of an expression (or a subexpression) in general includes both value computations [...] and initiation of side effects.*

一类是值计算（value computation）：算出表达式的值，或者确定它指向哪个对象。另一类是副作用（side effect）：改变某种状态。

标准列举了哪些操作是副作用：

> *Reading an object designated by a volatile glvalue, modifying an object, producing an injected declaration, calling a library I/O function, or calling a function that does any of those operations are all side effects, which are changes in the state of the execution or translation environment.*

也就是说，以下操作都是副作用：

- 读一个 `volatile` 对象
- 修改一个对象：比如 `i = 1`、`++i`、`v.push_back(x)`。
- 注入一个声明（涉及到 C++26 的反射，下文不再详述）
- 调用 I/O 函数：比如 `printf`、写文件、输出到 `std::cout`。
- 任何会做以上操作的函数

回到上文的 `i++`，它实际上做了两件事：

- 值计算：计算出 `i` 的旧值
- 副作用：把 `i` 的值加一

这就是 `i++` 容易出问题的地方：它不是单纯读，也不是单纯写，而是“读出旧值”和“修改对象”绑在了一起。

## 可观察行为：编译器必须兑现的承诺

[可观察行为](https://eel.is/c++draft/intro.abstract#8)和副作用密切相关，范围却窄得多。标准专门把它限定为这么几类：

> *Accesses through volatile glvalues are evaluated strictly according to the rules of the abstract machine.*

> *Data is delivered to the host environment to be written into files.*

> *The input and output dynamics of interactive devices shall take place in such a fashion that prompting output is actually delivered before a program waits for input. What constitutes an interactive device is implementation-defined.*

即：

- 对 `volatile` 对象的访问
- 写文件
- 交互式设备的输入输出次序

别的副作用，只要外面观察不到，实现就有可能将其优化掉，看个例子：

```cpp
int x = 0;
x = 1; 
x = 2;
```

`x = 1` 修改了对象，是副作用。但它立刻被 `x = 2` 覆盖，中间那个 `1` 谁也观察不到，于是编译器可以把 `x = 1` 这次写入直接删掉（术语叫死存储消除，dead store elimination）。这里没有不透明的函数调用，删的就是这一次写本身；要是换成一次 `printf`，那就是可观察行为，一次都不能省。

所以对实现的优化来说，最终不能动的只有可观察行为，执行顺序、中间状态、用了几条指令、跑多快都可以变。但这不等于源码语义就没了约束：普通对象的值、求值的先后，仍然照标准规则来，实现只是有自由用任何方式，最终把它们兑现成一致的可观察结果。

这套设计到此就完整了。as-if 只保证可观察行为的正确性；副作用和可观察行为这两个词，界定了哪些必须兑现、哪些可以随便改。没有它们，标准只剩两个都用不了的选择：要求实现逐条照你写的执行，慢到没法用；或者放它随便来，连 `printf` 都可能不发生。有了这条线，C++ 才能在保证正确的同时留出优化空间。

## 求值顺序：偏序，不是全序

现在回到最初的问题：一个表达式里，这些动作到底谁先谁后？

同一个线程里的先后，标准叫 [sequenced-before](https://eel.is/c++draft/intro.execution#8)：

> *Sequenced before is an asymmetric, transitive, pair-wise relation between evaluations executed by a single thread [...] if A is sequenced before B [...], then the execution of A shall precede the execution of B.*

A sequenced-before B，就是 A 一定排在 B 前面。注意标准用的词：它说 sequenced-before 是个偏序（partial order）。

偏序和全序的区别在于，全序是任意两个元素都有确定的顺序，而偏序只规定了一部分元素之间的顺序。

C++ 的求值就是偏序的。标准不会把一个表达式里的所有子求值排成一条队，它只钉死其中一部分，剩下的谁先谁后，不作规定。这种没被排先后的关系，标准叫 unsequenced：

> *If A is not sequenced before B and B is not sequenced before A, then A and B are unsequenced.*

比如：

```cpp
int cost = price(order) + shipping(order);
```

`+` 的左右操作数就是 unsequenced：`price(order)` 和 `shipping(order)` 谁先调用，标准不承诺。

还有第三种，介于两者之间，叫 indeterminately sequenced，两者一定有先后，但标准不告诉你谁前谁后：

> *Evaluations A and B are indeterminately sequenced when either A is sequenced before B or B is sequenced before A, but it is unspecified which.*

三个词放一起：

- unsequenced： 是没排队，两件事可能交错。
- indeterminately sequenced： 排了队，但不告诉你谁前谁后。
- sequenced-before： 有明确的先后。

这里真正会出问题的就是 unsequenced。

## 常见的求值顺序

按标准条款一条条过，每条配个例子。先看有确定顺序的。

[语句之间](https://eel.is/c++draft/intro.execution#9)：前一个完整表达式的全部动作，先于下一个。

```cpp
buffer.append(line);   // 先做完
socket.send(buffer);   // 再开始
```

逻辑运算符 [&&](https://eel.is/c++draft/expr.log.and#1)、[||](https://eel.is/c++draft/expr.log.or#1) ：左操作数先求值，左边定了结果就短路，右边不求值。

```cpp
if (p && p->valid()) { /* p 为空就不会去解引用 */ }
```

[逗号 `,`](https://eel.is/c++draft/expr.comma#1)：左表达式先于右表达式求值。

```cpp
for (int i = 0, j = n - 1; i < j; ++i, --j) { /* ++i 先于 --j */ }
```

[条件 `?:`](https://eel.is/c++draft/expr.cond#1)：先求值条件表达式，再只算被选中的那个分支。

```cpp
int timeout = fast ? 10 : slow_default();   // fast 为真时 slow_default() 不执行
```

[赋值 `=`](https://eel.is/c++draft/expr.assign#1)（C++17 起）：右操作数先于左操作数求值，赋值动作排在两边求值之后。

```cpp
data[index()] = compute();   // compute() 先于 index()
```

[移位运算符 `<<`、`>>`](https://eel.is/c++draft/expr.shift#4)（C++17 起）：左操作数先于右操作数求值。

```cpp
std::cout << first() << second();   // first() 先于 second()
```

[下标运算符 `[]`](https://eel.is/c++draft/expr.sub)（C++17 起）：`a[b]` 里 `a` 先于 `b`。

```cpp
select(id)[offset()];   // select(id) 先于 offset()
```

[函数调用](https://eel.is/c++draft/expr.call#7)：表示被调函数的那个表达式，先于所有实参求值。

```cpp
get_func(id)(compute());   // get_func(id) 先于实参 compute()
```

再看没有确定顺序的，这两类最容易栽。

普通二元运算 `a + b`、`a * b` 等：左右操作数之间无序（unsequenced），标准没给它们定序。

```cpp
int total = left() + right();   // left() 和 right() 谁先，不指定
```

[函数各实参之间](https://eel.is/c++draft/expr.call#7)（C++17 起）：是 indeterminately sequenced，一个会完整排在另一个前，但不指定哪个在前。C++17 之前这里更凶，实参之间是 unsequenced，`f(i++, i++)` 直接是 UB。

```cpp
f(parse_a(), parse_b());   // parse_a() 和 parse_b() 谁先，不指定
```

两者的差别很重要：无序（`a + b`）可能撞上未定义行为；不确定序（函数实参）不会因此变成 UB，但结果可能是 unspecified 的，顺序不定、值也就不定，一样不能依赖。

## 副作用对求值顺序的影响

到这里得把两条线索接起来。前面讲了求值顺序，也讲了副作用。单线程里，求值顺序会不会影响结果，取决于有没有副作用。

一个表达式里如果只有值计算、没有副作用，那谁先算都不影响结果，比如：

```cpp
int total = pure_left() + pure_right();
```

`+` 的左右操作数是 unsequenced，但只要 `pure_left()` 和 `pure_right()` 都是纯计算、不碰任何状态，谁先求值都得到同一个和。

副作用一进来就不同了。一个求值改了状态，另一个求值又依赖这个状态（读它，或者也改它），两者之间要是没有确定的先后，结果就说不清。C++ 把这种“说不清”直接判成[未定义行为](https://eel.is/c++draft/intro.execution#10)：

> *The behavior is undefined if a side effect on a memory location [...] is unsequenced relative to another side effect on the same memory location [...] or a value computation using the value of any object in the same memory location [...]*

拆开看对应两种情况：同一个对象上，两个副作用无序，UB；一个副作用和一次读它的值计算无序，也 UB。所以危险的不只是“改两次”，“一边改一边读”一样危险。

对应到最基本的两种写法：

```cpp
int x = i++ + i++;   // 两个副作用无序，UB
int y = i++ + i;     // 一个副作用、一个读，无序，同样 UB
```

`i++ + i` 尤其容易漏：右边的 `i` 只是读，可它读的值计算和左边 `i++` 的写是无序的，照样中招。这就是那些“经典面试题”的真相：它们根本没有标准答案。

## 回到 i = i++

现在能把开头那行拆清楚了：

```cpp
int i = 0;
i = i++;
```

先看右边的 `i++`，[后自增](https://eel.is/c++draft/expr.post.incr#1) 本身是有序的：

> *The value computation of the ++ expression is sequenced before the modification of the operand object.*

也就是先给出旧值，再改对象。但外层还套了一次赋值，赋值本身也是副作用，它要改左边的 `i`。

C++17 之前，右边 `i++` 改 `i`、外层赋值也改 `i`，这两次修改没有明确先后，于是整行是未定义行为。

C++17 收紧了[赋值顺序](https://eel.is/c++draft/expr.assign#1)：

> *The assignment is sequenced after the value computation of the right and left operands [...] The right operand is sequenced before the left operand.*

于是上面的代码就有了定义。设 `i` 从 0 开始：右边 `i++` 先求值，值计算得到旧值 `0`、副作用把 `i` 变成 `1`；再算左边，左边确定要写的对象是 `i`；最后赋值，把旧值 `0` 写回 `i`。绕一圈，`i` 还是 `0`。

有定义不代表值得写。它只是从“未定义”变成了“合法但没人看得懂”的代码。要读者翻标准才能算出结果的表达式，本身就该避免。

## C++17 到底改了什么

上一节标「C++17 起」的那几条定序（赋值、移位、下标、函数实参），都来自 C++17 的提案 P0145（更早的 C++03 用“序列点”，C++11 换成 sequenced-before）。补上顺序后，一批老写法从“未定义”变成了“有定义”。

[函数调用](https://eel.is/c++draft/expr.call#7)这条需要单独说清楚：

> *The postfix-expression is sequenced before each expression in the expression-list and any default argument. The initialization of a parameter [...] is indeterminately sequenced with respect to that of any other parameter.*

它说的不是“函数体先于实参”（函数体当然得等实参备齐），而是“决定调用哪个函数的那个表达式”先于实参。而实参之间只是 indeterminately sequenced：一个会完整排在另一个前面，但标准不告诉你哪个在前。于是这几行的性质变了：

```cpp
i = i++;                  // C++17 起有定义：i 不变
std::cout << i++ << i++;  // C++17 起有定义：从左到右
f(i++, i++);              // C++17 起不再 UB，但谁先算仍不指定
```

`f(i++, i++)` 值得多看一眼：它从“未定义”变成了“有定义但结果不定”，不再是 UB，可结果依然不该依赖。C++17 没堵上所有口子，普通算术运算符的操作数至今没有定序：

```cpp
int x = i++ + i++;   // 仍是 UB
int y = i++ + i;     // 仍是 UB
```

`+` 的左右没有先后，问题原封不动。

## 如何避免 UB

这些规则背着累，但落到实践，用不着记全。几条原则就够：

- 一个表达式里，别对同一个对象又读又写。`arr[i] = i++`、`f(i, i++)` 这种，即便某些写法在 C++17 后不再是 UB，也别写。
- 别依赖函数实参的求值顺序，它是不指定的。
- 宏参数里别放 `i++` 这类带副作用的东西，宏可能把参数展开好几次。
- `assert` 里别放有副作用的调用。发布版定义了 `NDEBUG`，整个表达式会消失，副作用也跟着没了。
- 短路要用清楚：`a() && b()` 里，`a()` 为假时 `b()` 不会执行，别把非做不可的副作用塞进 `b()`。

稳妥的写法往往很朴素：把纠缠的一步拆成几步，让顺序落在语句之间。

```cpp
int old = i++;
process(old, i);
```

不炫技，但谁先谁后一目了然，读者不用去翻标准。

## 总结

绕了一大圈，`i = i++` 等于几其实不重要。它真正牵出的是这篇的两样东西：副作用，和求值顺序。`i++` 不只是取一个值，还捎带一个改动 `i` 的副作用；而一个表达式内部，各个求值谁先谁后，标准只排了一部分。

两者一撞，就是所有麻烦的根：同一个对象上，两个副作用之间、或者一次修改和一次读取之间，只要标准没排先后，就是未定义行为。`i = i++`、`i++ + i++`、`f(i++, i++)` 都是这一条的不同写法。C++17 钉死了赋值、移位、下标、函数实参几处顺序，补掉一批，但普通算术运算符的操作数至今没排，`i++ + i++` 依旧 UB。

顺序为什么留得这么松？因为 C++ 不把你的代码当成一条条照做的指令，而当成一份要交付的结果：只要可观察行为兑现，中间怎么重排、合并、删都随实现的便，优化的空间正来自这里。副作用、可观察行为、sequenced-before 这几个词，就是在“必须兑现”和“可以随便改”之间划的那条线。所以看到一个表达式，别急着算它等于几，先看清哪里有副作用、它们之间排没排顺序，这才是 `i = i++` 这类问题真正在考的东西。
