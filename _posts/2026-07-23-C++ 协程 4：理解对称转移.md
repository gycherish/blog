协程 TS 让异步代码可以写得接近同步代码。在合适的位置加上 `co_await`，编译器便会负责挂起协程、保存跨挂起点的状态，并在操作完成后恢复执行。

不过，最初版本的协程 TS 有一项棘手限制，稍不注意就会导致栈溢出。为了在 `task<T>` 类型中可靠地避开它，实现者不得不付出额外的同步成本。

2018 年，协程设计加入了“对称转移”（symmetric transfer）：挂起一个协程并恢复另一个协程时，不再额外消耗栈空间。这项能力解除了协程 TS 的一项关键限制，让异步协程类型的实现更简单、更高效，同时仍能安全地防止栈溢出。

本文先还原栈溢出的成因，再看对称转移如何解决它。

## task 协程如何工作

考虑以下协程：
```c++
task foo() {
  co_return;
}

task bar() {
  co_await foo();
}
```

假设有一个简单的 `task` 类型。它采用惰性执行，只有另一个协程开始等待时才运行协程体；这个版本不支持返回值。

下面顺着执行过程，看看 `bar()` 求值 `co_await foo()` 时会发生什么。

* `bar()` 协程调用 `foo()`。从调用方看，调用协程与调用普通函数没有区别。
* `foo()` 的调用执行几个步骤：
  * 为协程帧分配存储空间，通常位于堆上；
  * 把参数复制到协程帧，本例没有参数，这一步不做任何事；
  * 在协程帧中构造 Promise 对象；
  * 调用 `promise.get_return_object()` 取得 `foo()` 的返回对象。这个调用创建一个 `task`，并用指向新协程帧的 `std::coroutine_handle` 初始化它；
  * 在初始挂起点，也就是左花括号处挂起协程；
  * 把 `task` 对象返回给 `bar()`。
* 接下来，`bar()` 对 `foo()` 返回的 `task` 求值 `co_await`。
  * `bar()` 先挂起，再调用该 `task` 的 `await_suspend()`，并传入指向 `bar()` 协程帧的 `std::coroutine_handle`；
  * `await_suspend()` 把 `bar()` 的句柄存入 `foo()` 的 Promise 对象，然后对 `foo()` 的句柄调用 `.resume()`，恢复 `foo()`。
* `foo()` 同步执行直至结束。
* `foo()` 在最终挂起点，也就是右花括号处挂起，再恢复启动前存入 Promise 对象的那个句柄，也就是 `bar()`。
* `bar()` 恢复执行。到达 `co_await` 所在语句的末尾时，从 `foo()` 返回的临时 `task` 被析构。
* `task` 析构函数对 `foo()` 的协程句柄调用 `.destroy()`，销毁协程帧、Promise 对象和参数副本。

一个简单调用背后已经有不少步骤。

为了看清各步之间的关系，下面用不支持对称转移的协程 TS 设计实现一个简化版 `task`。

## `task` 的结构

类的轮廓如下：
```c++
class task {
public:
  class promise_type { /* see below */ };

  task(task&& t) noexcept
  : coro_(std::exchange(t.coro_, {}))
  {}

  ~task() {
    if (coro_)
      coro_.destroy();
  }

  class awaiter { /* see below */ };

  awaiter operator co_await() && noexcept;

private:
  explicit task(std::coroutine_handle<promise_type> h) noexcept
  : coro_(h)
  {}

  std::coroutine_handle<promise_type> coro_;
};
```

`task` 独占一个 `std::coroutine_handle`，它指向调用协程时创建的协程帧。`task` 是 RAII 对象，离开作用域时会对句柄调用 `.destroy()`。

接下来补全 `promise_type`。

## 实现 `task::promise_type`

[上一篇文章](/blog/posts/C++-协程-3-理解-promise-类型/)已经介绍过，`promise_type` 指定了协程帧中 Promise 对象的类型，而 Promise 对象负责控制协程行为。

先实现 `get_return_object()`，构造协程调用要返回的 `task`。它只需用新协程帧的 `std::coroutine_handle` 初始化 `task`。

通过 `std::coroutine_handle::from_promise()` 可以从 Promise 对象取得这个句柄。

```c++
class task::promise_type {
public:
  task get_return_object() noexcept {
    return task{std::coroutine_handle<promise_type>::from_promise(*this)};
  }
```

协程应先在左花括号处挂起，等返回的 `task` 被等待时再从这里恢复。

惰性启动有几个好处：
1. 可以在协程开始执行前挂接后续协程的 `std::coroutine_handle`，不需要用线程同步处理“后续协程尚未挂接，当前协程已经结束”的竞争；
2. `task` 析构函数可以无条件销毁协程帧。协程被等待前不会启动；开始执行后，调用它的协程处于挂起状态，不会在任务完成前析构 `task`。明确的生命周期也让编译器更有机会把协程帧内嵌进调用方的帧中。堆分配消除优化（Heap Allocation eLision Optimization，HALO）详见 [P0981R0](https://wg21.link/P0981R0)；
3. 异常安全性更好。如果调用方没有立即 `co_await` 返回的 `task`，而是先执行其他可能抛异常的操作，栈展开会析构 `task`。此时可以安全销毁协程，因为它还没有启动；实现者不必在分离任务、留下悬空引用、让析构函数阻塞、调用 `std::terminate` 和触发未定义行为之间艰难取舍。我的 [CppCon 2019 结构化并发演讲](https://www.youtube.com/watch?v=1Wy5sq3s2rg)对此有更详细的讨论。

要让协程最初挂在左花括号处，`initial_suspend()` 返回内置的 `suspend_always`。

```c++
  std::suspend_always initial_suspend() noexcept {
    return {};
  }
```

随后定义 `return_void()`，执行 `co_return;` 或越过协程体末尾时会调用它。这个方法无需做任何事；只要它存在，编译器就知道该协程类型允许 `co_return;`。

```c++
  void return_void() noexcept {}
```

异常逃出协程体时会调用 `unhandled_exception()`。这个简化实现把任务协程体视为 `noexcept`，遇到未处理异常就调用 `std::terminate()`。

```c++
  void unhandled_exception() noexcept {
    std::terminate();
  }
```

最后，协程执行到右花括号时，要在最终挂起点挂起，再恢复等待它完成的后续协程。

为此，需要一个数据成员保存后续协程的 `std::coroutine_handle`。`final_suspend()` 则返回一个 Awaitable，在当前协程到达最终挂起点后恢复这个后续协程。

必须等当前协程挂起后才能恢复后续协程。后续协程可能立即析构 `task`，进而对当前协程帧调用 `.destroy()`；而 `.destroy()` 只能作用于已挂起的协程。提前恢复后续协程会导致未定义行为。

编译器会在右花括号处插入 `co_await promise.final_suspend();`。

调用 `final_suspend()` 时，协程还没有挂起。直到编译器调用返回对象的 `await_suspend()`，协程才进入已挂起状态。

```c++
  struct final_awaiter {
    bool await_ready() noexcept {
      return false;
    }

    void await_suspend(std::coroutine_handle<promise_type> h) noexcept {
      // The coroutine is now suspended at the final-suspend point.
      // Lookup its continuation in the promise and resume it.
      h.promise().continuation.resume();
    }

    void await_resume() noexcept {}
  };

  final_awaiter final_suspend() noexcept {
    return {};
  }

  std::coroutine_handle<> continuation;
};
```

至此 `promise_type` 已经完整，只剩 `task::operator co_await()`。

## 实现 `task::operator co_await()`

[《理解 operator co_await》](/blog/posts/C++-协程-2-理解-operator-co_await/)提到，求值 `co_await` 时，如果类型定义了 `operator co_await()`，编译器就会调用它；返回对象必须提供 `await_ready()`、`await_suspend()` 和 `await_resume()`。

协程等待 `task` 时，等待方总是先挂起。挂起后，把等待方句柄存入即将恢复的任务协程之 Promise 对象，再对 `task` 的 `std::coroutine_handle` 调用 `.resume()`，开始执行任务。

代码很直接：
```c++
class task::awaiter {
public:
  bool await_ready() noexcept {
    return false;
  }

  void await_suspend(std::coroutine_handle<> continuation) noexcept {
    // Store the continuation in the task's promise so that the final_suspend()
    // knows to resume this coroutine when the task completes.
    coro_.promise().continuation = continuation;

    // Then we resume the task's coroutine, which is currently suspended
    // at the initial-suspend-point (ie. at the open curly brace).
    coro_.resume();
  }

  void await_resume() noexcept {}

private:
  explicit awaiter(std::coroutine_handle<task::promise_type> h) noexcept
  : coro_(h)
  {}

  std::coroutine_handle<task::promise_type> coro_;
};

task::awaiter task::operator co_await() && noexcept {
  return awaiter{coro_};
}
```

这样就完成了这个只表示完成、不产生值的 `task` 类型。

完整代码可在 [Compiler Explorer](https://godbolt.org/z/-Kw6Nf) 中查看。

## 栈溢出问题

如果协程中存在循环，而循环体里 `co_await` 的任务可能同步完成，这个实现的限制就暴露出来了。

例如：
```c++
task completes_synchronously() {
  co_return;
}

task loop_synchronously(int count) {
  for (int i = 0; i < count; ++i) {
    co_await completes_synchronously();
  }
}
```

使用上面的简化 `task`，`count` 为 10、1000 甚至 100'000 时，`loop_synchronously()` 也许都能正常运行。但参数继续增大，协程最终会崩溃。

例如，这份 [Compiler Explorer 示例](https://godbolt.org/z/gy5Q8q)在 `count` 为 1'000'000 时会崩溃。

原因是栈溢出。

要理解栈为什么会溢出，需要跟踪执行期间的栈帧变化。

`loop_synchronously()` 第一次开始执行，是因为另一个协程对它返回的 `task` 执行了 `co_await`。等待方先挂起并调用 `task::awaiter::await_suspend()`，后者再对任务的 `std::coroutine_handle` 调用 `resume()`。

因此，`loop_synchronously()` 启动时的栈如下：
```
           Stack                                                   Heap
+------------------------------+  <-- top of stack   +--------------------------+
| loop_synchronously$resume    | active coroutine -> | loop_synchronously frame |
+------------------------------+                     | +----------------------+ |
| coroutine_handle::resume     |                     | | task::promise        | |
+------------------------------+                     | | - continuation --.   | |
| task::awaiter::await_suspend |                     | +------------------|---+ |
+------------------------------+                     | ...                |     |
| awaiting_coroutine$resume    |                     +--------------------|-----+
+------------------------------+                                          V
|  ....                        |                     +--------------------------+
+------------------------------+                     | awaiting_coroutine frame |
                                                     |                          |
                                                     +--------------------------+
```

> 注意：编译协程函数时，编译器通常把它拆成两部分：
> 1. “ramp function”，负责构造协程帧、复制参数、构造 Promise 并生成返回对象；
> 2. “coroutine body”，即包含用户代码的协程状态机。
>
> 下图用 `$resume` 后缀表示协程体部分。后续文章会详细解释这次拆分。

当 `loop_synchronously()` 等待 `completes_synchronously()` 返回的 `task` 时，当前协程挂起并调用 `task::awaiter::await_suspend()`。该方法再对 `completes_synchronously()` 的协程句柄调用 `.resume()`。

`completes_synchronously()` 随即恢复，同步运行到结束并停在最终挂起点。接着调用 `task::promise::final_awaiter::await_suspend()`，后者对 `loop_synchronously()` 的句柄调用 `.resume()`。

如果在 `loop_synchronously()` 恢复之后、`completes_synchronously()` 返回的临时 `task` 在分号处销毁之前观察程序，栈和堆大致如下：
```
           Stack                                                   Heap
+-------------------------------+ <-- top of stack
| loop_synchronously$resume     | active coroutine -.
+-------------------------------+                   |
| coroutine_handle::resume      |            .------'
+-------------------------------+            |
| final_awaiter::await_suspend  |            |
+-------------------------------+            |  +--------------------------+ <-.
| completes_synchronously$resume|            |  | completes_synchronously  |   |
+-------------------------------+            |  | frame                    |   |
| coroutine_handle::resume      |            |  +--------------------------+   |
+-------------------------------+            '---.                             |
| task::awaiter::await_suspend  |                V                             |
+-------------------------------+ <-- prev top  +--------------------------+   |
| loop_synchronously$resume     |     of stack  | loop_synchronously frame |   |
+-------------------------------+               | +----------------------+ |   |
| coroutine_handle::resume      |               | | task::promise        | |   |
+-------------------------------+               | | - continuation --.   | |   |
| task::awaiter::await_suspend  |               | +------------------|---+ |   |
+-------------------------------+               | - task temporary --|---------'
| awaiting_coroutine$resume     |               +--------------------|-----+
+-------------------------------+                                    V
|  ....                         |               +--------------------------+
+-------------------------------+               | awaiting_coroutine frame |
                                                |                          |
                                                +--------------------------+
```

下一步会调用 `task` 析构函数，销毁 `completes_synchronously()` 的协程帧。随后 `count` 递增，循环再次创建并恢复一个新的 `completes_synchronously()` 帧。

实际发生的是 `loop_synchronously()` 与 `completes_synchronously()` 递归地恢复对方。每次往返都会多占一层栈空间；迭代足够多后，栈溢出，程序进入未定义行为，通常立即崩溃。

这种协程实现让一段表面只有循环的代码，在不知不觉中形成无界递归。

最初的协程 TS 设计要怎样绕开这个问题？

## 协程 TS 中的解决办法

关键是停止两个协程之间的无界递归。

上面的实现使用返回 `void` 的 `await_suspend()`。协程 TS 还允许它返回 `bool`：返回 `true` 时协程保持挂起，控制权回到 `resume()` 调用方；返回 `false` 时当前协程立即恢复，而且不会额外消耗栈空间。

因此，如果任务同步完成，可以让 `task::awaiter::await_suspend()` 返回 `false` 来恢复当前协程，不再通过 `std::coroutine_handle::resume()` 递归恢复它。

通用实现分成两部分。

1. `task::awaiter::await_suspend()` 调用 `.resume()` 启动任务协程。`.resume()` 返回后检查任务是否已经结束：结束就返回 `false`，立即恢复等待方；尚未结束则返回 `true`，把控制权交回 `std::coroutine_handle::resume()` 的调用方。

2. 任务协程结束时，`task::promise_type::final_awaiter::await_suspend()` 检查等待方的 `task::awaiter::await_suspend()` 是否已经或即将返回 `true`。如果是，就调用 `.resume()` 恢复等待方；否则不要恢复，而要通知等待方返回 `false`。

还有一项并发复杂性：任务协程可能先在当前线程运行并挂起，之后在另一线程恢复，并在最初那次 `.resume()` 返回前结束。上面两部分可能同时发生，必须处理它们之间的竞争。

这里需要一个 `std::atomic` 值来仲裁竞争。


代码需要做如下修改：
```c++
class task::promise_type {
  ...

  std::coroutine_handle<> continuation;
  std::atomic<bool> ready = false;
};

bool task::awaiter::await_suspend(
  std::coroutine_handle<> continuation) noexcept {
  promise_type& promise = coro_.promise();
  promise.continuation = continuation;
  coro_.resume();
  return !promise.ready.exchange(true, std::memory_order_acq_rel);
}

void task::promise_type::final_awaiter::await_suspend(
  std::coroutine_handle<promise_type> h) noexcept {
  promise_type& promise = h.promise();
  if (promise.ready.exchange(true, std::memory_order_acq_rel)) {
    // The coroutine did not complete synchronously, resume it here.
    promise.continuation.resume();
  }
}
```

更新后的 [Compiler Explorer 示例](https://godbolt.org/z/7fm8Za)在 `count == 1'000'000` 时不再崩溃。

`cppcoro::task<T>` 的[实现](https://github.com/lewissbaker/cppcoro/blob/master/include/cppcoro/task.hpp)曾经采用这套办法来避免无界递归，在某些平台上现在仍然如此，实际效果不错。

看起来问题已经解决，可以交付了。可惜还没这么简单。

## 这套办法的代价

原子状态机解决了递归，却带来几项代价。

第一，`std::atomic` 操作可能相当昂贵。等待方挂起时要做一次原子交换，任务运行结束时再做一次。即便应用始终在单线程上运行，从来不需要线程同步，也要承担这份成本。

第二，代码多了分支。等待方要决定保持挂起还是立即恢复，任务一方也要决定恢复后续协程还是继续挂起。

多数时候，业务逻辑的成本远高于这些分支，甚至也高于原子操作。不过，协程的目标是零成本抽象，有些人甚至用协程挂起函数，避免原地等待 L1 缓存未命中。Gor 的 [CppCon nano-coroutines 演讲](https://www.youtube.com/watch?v=j9tlJAqMV7U)展示了这种用法。

第三，也是可能最重要的一点：等待方会在哪个执行上下文中恢复，变得不再确定。

假设我有以下代码：
```c++
cppcoro::static_thread_pool tp;

task foo()
{
  std::cout << "foo1 " << std::this_thread::get_id() << "\n";
  // Suspend coroutine and reschedule onto thread-pool thread.
  co_await tp.schedule();
  std::cout << "foo2 " << std::this_thread::get_id() << "\n";
}

task bar()
{
  std::cout << "bar1 " << std::this_thread::get_id() << "\n";
  co_await foo();
  std::cout << "bar2" << std::this_thread::get_id() << "\n";
}
```

原始实现保证 `co_await foo()` 之后的代码内联运行在 `foo()` 完成时所在的线程。

例如，一种可能的输出是：
```
bar1 1234
foo1 1234
foo2 3456
bar2 3456
```

改成原子状态机后，`foo()` 的完成可能与 `bar()` 的挂起竞争。某些时序下，`co_await foo()` 之后的代码会回到最初启动 `bar()` 的线程上运行。

例如，现在也可能出现以下输出：
```
bar1 1234
foo1 1234
foo2 3456
bar2 1234
```

很多场景并不在乎这个差异，但专门用于切换执行上下文的算法会受到影响。

例如，`via()` 先等待某个 Awaitable，再把结果送到指定调度器的执行上下文中。简化实现如下：
```c++
template<typename Awaitable, typename Scheduler>
task<await_result_t<Awaitable>> via(Awaitable a, Scheduler s)
{
  auto result = co_await std::move(a);
  co_await s.schedule();
  co_return result;
}

task<T> get_value();
void consume(const T&);

task<void> consumer(static_thread_pool::scheduler s)
{
  T result = co_await via(get_value(), s);
  consume(result);
}
```

原始版本保证 `consume()` 始终在线程池 `s` 上执行。改用原子状态机后，它既可能在调度器 `s` 关联的线程上执行，也可能回到启动 `consumer()` 的线程。

我们需要一种不依赖原子操作和额外分支、又能保持恢复上下文确定的栈溢出解决方案。

## 对称转移

Gor Nishanov 2018 年的论文 [P0913R0《Add symmetric coroutine control transfer》](https://wg21.link/P0913R0)提出了一种解决方案：让一个协程挂起后对称地恢复另一个协程，不再增加栈空间占用。

论文提出了两项关键修改：
* 允许 `await_suspend()` 返回 `std::coroutine_handle<T>`，表示控制权应对称转移到该句柄标识的协程；
* 增加 `std::experimental::noop_coroutine()`。它返回一种特殊的 `std::coroutine_handle`；`await_suspend()` 返回该句柄时，当前协程挂起，控制权回到 `.resume()` 调用方，而不会转移到另一个协程。

“对称”具体指什么？

通过 `std::coroutine_handle` 的 `.resume()` 恢复协程时，`.resume()` 的调用方仍然活跃在栈上。目标协程下次挂起，如果挂起点的 `await_suspend()` 返回 `void`，或返回 `true` 表示保持挂起，这次 `.resume()` 调用才会返回。

这可以看成向协程执行一次“非对称转移”，行为与普通函数调用相似。`.resume()` 的调用方可以是任意函数，不一定是协程。目标协程挂起后，控制权沿着 `.resume()` 调用关系返回。

每调用一次 `.resume()`，都会为目标协程的执行创建一个新栈帧。

对称转移则只是挂起一个协程、恢复另一个协程，两者之间没有隐式的调用方与被调用方关系。协程挂起时可以把控制权交给任意已挂起协程，包括自己；它下次挂起或结束时，也不必回到先前那个协程。

Awaiter 使用对称转移时，编译器会把 `co_await` 大致降低成下面的形式：

```c++
{
  decltype(auto) value = <expr>;
  decltype(auto) awaitable = get_awaitable(promise, static_cast<decltype(value)&&>(value));
  decltype(auto) awaiter = get_awaiter(static_cast<decltype(awaitable)&&>(awaitable));
  if (!awaiter.await_ready())
  {
    using handle_t = std::coroutine_handle<P>;

    //<suspend-coroutine>

    auto h = awaiter.await_suspend(handle_t::from_promise(p));
    h.resume();
    //<return-to-caller-or-resumer>
    
    //<resume-point>
  }

  return awaiter.await_resume();
}
```

其中与其他 `co_await` 形式不同的关键部分是：
```c++
auto h = awaiter.await_suspend(handle_t::from_promise(p));
h.resume();
//<return-to-caller-or-resumer>
```

协程状态机降低后，这里的 `<return-to-caller-or-resumer>` 基本会变成一条 `return;`，使最后一次恢复当前协程的 `.resume()` 返回它的调用方。状态机降低是后续文章的主题。

于是形成这样的代码形状：当前函数本身是一次 `std::coroutine_handle::resume()` 所进入的协程体，它在末尾调用签名相同的另一个 `std::coroutine_handle::resume()`，紧接着 `return;`。

满足一定条件时，编译器可以把位于尾部位置，也就是函数返回前的调用，优化成尾调用。

尾调用恰好能避免前面的栈溢出。不过这里不能依赖优化器的判断；即使没有开启优化，也需要保证转换一定发生。

先明确什么是尾调用。

### 尾调用

尾调用会在进入被调用函数前弹出当前栈帧，并把当前函数的返回地址交给被调用函数。被调用函数结束后，直接返回当前函数的调用方。

在 x86/x64 上，编译器通常先弹出当前栈帧，再用 `jmp` 跳到目标函数入口，而不是发出 `call`，等调用返回后再弹栈。

尾调用只在有限条件下成立。

特别是，它要求：
* 调用约定支持尾调用，而且调用方与被调用方使用相同的调用约定；
* 返回类型相同；
* 调用结束、返回上层之前，不需要再运行任何非平凡析构函数；
* 调用不位于 `try`/`catch` 块内。

`co_await` 的对称转移形式正是按这些条件设计的。下面逐项检查。

**调用约定。** 编译器把协程降低成机器代码时，会将它拆成两部分：ramp function 负责分配并初始化协程帧，coroutine body 则包含由用户协程体转换而来的状态机。

协程的函数签名以及用户指定的调用约定只影响 ramp function。coroutine body 完全由编译器控制，用户代码不会直接调用它，只有 ramp function 和 `std::coroutine_handle::resume()` 会进入这部分。

coroutine body 的调用约定对用户不可见，编译器可以为所有协程体选择一套支持尾调用的约定。

**返回类型相同。** 源协程和目标协程的 `.resume()` 都返回 `void`，这项条件天然满足。

**没有待执行的非平凡析构函数。** 尾调用必须在进入目标函数前释放当前栈帧，因此所有栈上对象的生命周期都要在调用前结束。

通常，只要作用域内还有带非平凡析构函数的对象，这个条件就难以满足：对象位于栈上，生命周期也还没有结束。

协程挂起时并不退出作用域。为了保留这些对象，编译器会把生命周期跨越挂起点的对象放进协程帧，而非栈帧。

生命周期不跨越挂起点的局部变量可以放在栈上，但协程下次挂起前，它们的生命周期已经结束，析构函数也已执行。

因此，执行对称转移时，不会留下需要在尾调用返回后再析构的栈上对象。

**调用不在 `try`/`catch` 块内。** 这一项稍复杂，因为每个协程都有一个隐式 `try`/`catch`，包住用户编写的协程体。

规范给出的转换大致如下：
```c++
{
  promise_type promise;
  co_await promise.initial_suspend();
  try { F; }
  catch (...) { promise.unhandled_exception(); }
final_suspend:
  co_await promise.final_suspend();
}
```

其中 `F` 是用户编写的协程体。

因此，除初始挂起和最终挂起外，用户写下的每个 `co_await` 都位于 `try`/`catch` 上下文中。

实现会把 `.resume()` 的调用真正放到 `try` 块上下文之外，从而满足尾调用条件。

协程降低为机器代码时如何做到这一点，留到后续文章再详细讨论。

> 需要说明的是，当时 C++ 规范的正文并没有明确要求实现这样做，只有一条非规范性注释暗示这可能是必要的。希望未来能修正规范措辞。

由此可见，对称转移通常满足尾调用的全部条件。无论是否开启优化，编译器都保证这里采用尾调用。

让 `await_suspend()` 返回 `std::coroutine_handle`，就能挂起当前协程并把控制权交给另一个协程，同时不增加栈空间占用。

协程因此可以任意深度地相互恢复，而不会造成栈溢出。

这正是 `task` 实现所缺的能力。

## 重新实现 `task`

有了对称转移，现在可以回头修复 `task`。

实现中的两个 `await_suspend()` 都要修改：
* 等待任务时，通过对称转移恢复任务协程；
* 任务协程结束时，再通过对称转移恢复等待方。

先修改等待方向的 `task::awaiter`：
```c++
void task::awaiter::await_suspend(
  std::coroutine_handle<> continuation) noexcept {
  // Store the continuation in the task's promise so that the final_suspend()
  // knows to resume this coroutine when the task completes.
  coro_.promise().continuation = continuation;

  // Then we resume the task's coroutine, which is currently suspended
  // at the initial-suspend-point (ie. at the open curly brace).
  coro_.resume();
}
```
改成：
```c++
std::coroutine_handle<> task::awaiter::await_suspend(
  std::coroutine_handle<> continuation) noexcept {
  // Store the continuation in the task's promise so that the final_suspend()
  // knows to resume this coroutine when the task completes.
  coro_.promise().continuation = continuation;

  // Then we tail-resume the task's coroutine, which is currently suspended
  // at the initial-suspend-point (ie. at the open curly brace), by returning
  // its handle from await_suspend().
  return coro_;
}
```

返回路径上的 `task::promise_type::final_awaiter` 也要更新：
```c++
void task::promise_type::final_awaiter::await_suspend(
  std::coroutine_handle<promise_type> h) noexcept {
  // The coroutine is now suspended at the final-suspend point.
  // Lookup its continuation in the promise and resume it.
  h.promise().continuation.resume();
}
```
改成：
```c++
std::coroutine_handle<> task::promise_type::final_awaiter::await_suspend(
  std::coroutine_handle<promise_type> h) noexcept {
  // The coroutine is now suspended at the final-suspend point.
  // Lookup its continuation in the promise and resume it symmetrically.
  return h.promise().continuation;
}
```

现在的 `task` 既没有返回 `void` 的 `await_suspend()` 所导致的栈溢出，也没有返回 `bool` 的版本所带来的恢复上下文不确定性。


### 观察栈的变化

回到最初的例子：
```c++
task completes_synchronously() {
  co_return;
}

task loop_synchronously(int count) {
  for (int i = 0; i < count; ++i) {
    co_await completes_synchronously();
  }
}
```

`loop_synchronously()` 第一次开始执行，是因为另一个协程等待了它返回的 `task`。另一个协程调用 `std::coroutine_handle::resume()` 恢复它，这次启动来自一次对称转移。

`loop_synchronously()` 启动时，栈如下：
```
           Stack                                                Heap
+---------------------------+  <-- top of stack   +--------------------------+
| loop_synchronously$resume | active coroutine -> | loop_synchronously frame |
+---------------------------+                     | +----------------------+ |
| coroutine_handle::resume  |                     | | task::promise        | |
+---------------------------+                     | | - continuation --.   | |
|     ...                   |                     | +------------------|---+ |
+---------------------------+                     | ...                |     |
                                                  +--------------------|-----+
                                                                       V
                                                  +--------------------------+
                                                  | awaiting_coroutine frame |
                                                  |                          |
                                                  +--------------------------+
```

执行 `co_await completes_synchronously()` 时，控制权会对称转移到 `completes_synchronously` 协程。

过程如下：
* 调用 `task::operator co_await()`，取得 `task::awaiter`；
* 挂起当前协程，调用 `task::awaiter::await_suspend()`，取得 `completes_synchronously` 的 `coroutine_handle`；
* 通过尾调用跳到 `completes_synchronously`。激活它的栈帧之前，先弹出 `loop_synchronously` 的栈帧。

`completes_synchronously` 恢复后的栈如下：
```
              Stack                                          Heap
                                            .-> +--------------------------+ <-.
                                            |   | completes_synchronously  |   |
                                            |   | frame                    |   |
                                            |   | +----------------------+ |   |
                                            |   | | task::promise        | |   |
                                            |   | | - continuation --.   | |   |
                                            |   | +------------------|---+ |   |
                                            `-, +--------------------|-----+   |
                                              |                      V         |
+-------------------------------+ <-- top of  | +--------------------------+   |
| completes_synchronously$resume|     stack   | | loop_synchronously frame |   |
+-------------------------------+ active -----' | +----------------------+ |   |
| coroutine_handle::resume      | coroutine     | | task::promise        | |   |
+-------------------------------+               | | - continuation --.   | |   |
|     ...                       |               | +------------------|---+ |   |
+-------------------------------+               | task temporary     |     |   |
                                                | - coro_       -----|---------`
                                                +--------------------|-----+
                                                                     V
                                                +--------------------------+
                                                | awaiting_coroutine frame |
                                                |                          |
                                                +--------------------------+
```

栈帧数量没有增加。

`completes_synchronously` 运行到右花括号后，会求值 `co_await promise.final_suspend()`。

当前协程随即挂起，并调用 `final_awaiter::await_suspend()`。该方法返回后续协程的 `std::coroutine_handle`，也就是指向 `loop_synchronously` 的句柄，再通过对称转移的尾调用恢复它。

`loop_synchronously` 恢复后的栈如下：
```
           Stack                                                   Heap
                                                   +--------------------------+ <-.
                                                   | completes_synchronously  |   |
                                                   | frame                    |   |
                                                   | +----------------------+ |   |
                                                   | | task::promise        | |   |
                                                   | | - continuation --.   | |   |
                                                   | +------------------|---+ |   |
                                                   +--------------------|-----+   |
                                                                        V         |
+----------------------------+  <-- top of stack   +--------------------------+   |
| loop_synchronously$resume  | active coroutine -> | loop_synchronously frame |   |
+----------------------------+                     | +----------------------+ |   |
| coroutine_handle::resume() |                     | | task::promise        | |   |
+----------------------------+                     | | - continuation --.   | |   |
|     ...                    |                     | +------------------|---+ |   |
+----------------------------+                     | task temporary     |     |   |
                                                   | - coro_       -----|---------`
                                                   +--------------------|-----+
                                                                        V
                                                   +--------------------------+
                                                   | awaiting_coroutine frame |
                                                   |                          |
                                                   +--------------------------+
```

`loop_synchronously` 恢复后，到达分号时首先析构 `completes_synchronously` 返回的临时 `task`。这会销毁对应的协程帧并释放内存，得到如下状态：
```
           Stack                                                   Heap
+---------------------------+  <-- top of stack   +--------------------------+
| loop_synchronously$resume | active coroutine -> | loop_synchronously frame |
+---------------------------+                     | +----------------------+ |
| coroutine_handle::resume  |                     | | task::promise        | |
+---------------------------+                     | | - continuation --.   | |
|     ...                   |                     | +------------------|---+ |
+---------------------------+                     | ...                |     |
                                                  +--------------------|-----+
                                                                       V
                                                  +--------------------------+
                                                  | awaiting_coroutine frame |
                                                  |                          |
                                                  +--------------------------+
```

执行回到 `loop_synchronously` 后，栈帧与协程帧的数量都和本轮开始时相同。每次迭代都是如此。

循环可以执行任意多次，空间占用始终为常量。

## 对称转移是 await_suspend 的通用形式

对称转移其实是 **Awaitable** 概念中最通用的形式，理论上可以表示 `await_suspend()` 返回 `void` 和 `bool` 的两种形式。

要说明这一点，先看 [P0913R0](https://wg21.link/P0913R0) 加入协程设计的另一个部分：`std::noop_coroutine()`。

### 结束转移链

使用对称转移时，每次协程挂起都会恢复另一个协程。可有时并没有下一个协程要执行，只需挂起当前协程，让控制权回到 `std::coroutine_handle::resume()` 的调用方。

返回 `void` 和 `bool` 的 `await_suspend()` 都能表达这种情况。对称转移如何表示它？

答案是使用 `std::noop_coroutine()` 产生的特殊内置句柄，称为“noop coroutine handle”。

它的 `.resume()` 会立即返回，恢复这个协程等同于空操作，实现通常只有一条 `ret` 指令，因此得名 noop。

`await_suspend()` 返回 `std::noop_coroutine()` 句柄时，控制权不会转移给另一个真正的协程，而会回到 `std::coroutine_handle::resume()` 的调用方。

### 表示 await_suspend 的其他形式

下面用对称转移分别表示 `await_suspend()` 的另外两种形式。

返回 `void` 的形式：
```c++
void my_awaiter::await_suspend(std::coroutine_handle<> h) {
  this->coro = h;
  enqueue(this);
}
```
可以改写成返回 `bool`：
```c++
bool my_awaiter::await_suspend(std::coroutine_handle<> h) {
  this->coro = h;
  enqueue(this);
  return true;
}
```
也可以改写成对称转移：
```c++
std::noop_coroutine_handle my_awaiter::await_suspend(
    std::coroutine_handle<> h) {
  this->coro = h;
  enqueue(this);
  return std::noop_coroutine();
}
```

返回 `bool` 的形式：
```c++
bool my_awaiter::await_suspend(std::coroutine_handle<> h) {
  this->coro = h;
  if (try_start(this)) {
    // Operation will complete asynchronously.
    // Return true to transfer execution to caller of
    // coroutine_handle::resume().
    return true;
  }

  // Operation completed synchronously.
  // Return false to immediately resume the current coroutine.
  return false;
}
```
可以改写成对称转移：
```c++
std::coroutine_handle<> my_awaiter::await_suspend(std::coroutine_handle<> h) {
  this->coro = h;
  if (try_start(this)) {
    // Operation will complete asynchronously.
    // Return std::noop_coroutine() to transfer execution to caller of
    // coroutine_handle::resume().
    return std::noop_coroutine();
  }

  // Operation completed synchronously.
  // Return current coroutine's handle to immediately resume
  // the current coroutine.
  return h;
}
```

### 为什么保留三种形式

既然对称转移是通用形式，`await_suspend()` 为什么还要保留返回 `void` 和 `bool` 的版本？

原因兼有历史、实用性与性能三方面。

返回 `void` 的版本完全可以用返回 `std::noop_coroutine_handle` 代替。两者向编译器表达的含义相同：当前协程无条件挂起，控制权回到 `std::coroutine_handle::resume()` 的调用方。

它得以保留，一部分是因为对称转移加入前已有代码在使用，另一部分是因为无条件挂起时返回 `void` 写起来更简短。

在某些场景下，返回 `bool` 也比对称转移更容易优化。

假设返回 `bool` 的 `await_suspend()` 定义在另一个翻译单元。编译器仍能在等待方协程中生成直接代码：挂起当前协程，调用 `await_suspend()`，返回后根据结果决定是否从下一段状态继续。只要结果为 `false`，编译器确切知道应该执行哪个代码块。

对称转移也要表达同样的两种结果：回到调用方，或恢复当前协程。区别是它返回 `std::noop_coroutine()` 或当前协程的句柄，而非 `true` 或 `false`；两个句柄都可转换为 `std::coroutine_handle<void>`。

由于 `await_suspend()` 位于另一翻译单元，编译器看不到返回句柄指向哪个协程。恢复时就要进行较昂贵的间接调用，还可能多出分支；返回 `bool` 的版本只需要一个直接分支。

未来也许能让对称转移达到同等性能。例如，把 `await_suspend()` 内联定义，让它调用一个非内联、返回 `bool` 的方法，再根据结果返回相应句柄。

例如：
```c++
struct my_awaiter {
  bool await_ready();

  // Compilers should in-theory be able to optimise this to the same
  // as the bool-returning version, but currently don't do this optimisation.
  std::coroutine_handle<> await_suspend(std::coroutine_handle<> h) {
    if (try_start(h)) {
      return std::noop_coroutine();
    } else {
      return h;
    }
  }

  void await_resume();

private:
  // This method is defined out-of-line in a separate translation unit.
  bool try_start(std::coroutine_handle<> h);
}
```

但当时的编译器，以 Clang 10 为例，还不能把这段代码优化到与等价 `bool` 版本一样高效。除非在非常紧密的循环里反复等待，通常很难观察到差异。


因此，当时的一般选择规则是：
* 需要无条件回到 `.resume()` 调用方时，让 `await_suspend()` 返回 `void`；
* 需要在回到 `.resume()` 调用方和恢复当前协程之间选择时，返回 `bool`；
* 需要恢复另一个协程时，返回句柄，使用对称转移。

## 总结

C++20 协程加入对称转移后，协程可以递归地相互恢复而不造成栈溢出。它是构造高效、安全的异步协程类型的关键能力，本文的 `task` 就是一个例子。
