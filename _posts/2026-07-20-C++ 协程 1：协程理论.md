这是 C++ 协程技术规范（C++ Coroutines TS）系列的第一篇。写作本文时，这项新语言特性正准备纳入 C++20 标准。本文依据的规范版本是 [N4680](http://www.open-std.org/jtc1/sc22/wg21/docs/papers/2017/n4680.pdf)。

这个系列会解释 C++ 协程的底层机制，也会展示如何在它之上构建实用的高层抽象，例如 [cppcoro](https://github.com/lewissbaker/cppcoro) 库提供的那些类型。

这一篇先讨论函数与协程的区别，以及两者支持哪些操作。理解这些基础概念后，我们才有一套合适的模型去分析 C++ 协程。

## 协程是函数的泛化

协程是函数的一种泛化：执行可以中途挂起，之后再从挂起处恢复。

下面会仔细解释这句话。在此之前，先回顾一下普通 C++ 函数如何工作。

## 普通函数

普通函数可以看成支持两种操作：**Call（调用）**和 **Return（返回）**。这里把“抛出异常”也宽泛地归入 **Return** 操作。

**Call** 操作会创建一个活动帧，暂停调用方，并把控制权转移到被调用函数的入口。

**Return** 操作把返回值交给调用方，销毁活动帧，再从调用点之后继续执行调用方。

下面分别说明这两种操作的具体过程。

### 活动帧

什么是“活动帧”？

可以把活动帧看成一块内存，其中保存着某一次函数调用的当前状态，包括传入的参数和局部变量。

普通函数的活动帧还包含返回地址，也就是函数返回后应该跳到哪条指令，以及调用方活动帧的地址。这些信息共同描述了本次函数调用的后续执行信息（continuation）：函数结束后，该回到哪个函数的哪一次调用继续运行。

普通函数的活动帧具有严格嵌套的生命周期，因此可以用一种高效的数据结构为每次调用分配和释放活动帧，这种数据结构就是栈（stack）。

分配在栈上的活动帧通常称为“栈帧”（stack frame）。

栈如此常用，以至于绝大多数，也许是全部 CPU 架构，都有一个专用寄存器指向栈顶。例如，x64 使用 `rsp` 寄存器。

为新活动帧分配空间时，只需按帧大小调整这个寄存器；释放活动帧时，再向相反方向调回去即可。

### Call 操作

一个函数调用另一个函数时，调用方得先为暂停自身执行做好准备。

这一步通常要把 CPU 寄存器中的值保存到内存，等调用方恢复执行时再加载回来。具体由调用方还是被调用方保存，取决于调用约定；从整体上看，它们都属于 **Call** 操作。

调用方还会把实参值写入新的活动帧，供被调用函数访问。

最后，调用方把自己的恢复点地址写入新活动帧，然后把控制权交给被调用函数。

在 x86/x64 架构中，最后这一步有专门的 `call` 指令。它把下一条指令的地址压入栈中，相应地调整栈指针，然后跳转到操作数指定的地址。

### Return 操作

函数执行 `return` 时，会先把返回值（如果有）放到调用方能够访问的位置。这个位置可能属于调用方的活动帧，也可能属于当前函数的活动帧。参数和返回值需要跨越两个活动帧的边界，因此两者之间的界线有时并不分明。

然后，函数销毁自己的活动帧：
* 销毁返回点仍在作用域内的局部变量；
* 销毁参数对象；
* 释放活动帧占用的内存。

最后，函数恢复调用方：
* 让栈指针重新指向调用方的活动帧，并恢复可能被当前函数改写的寄存器；
* 跳转到 **Call** 操作保存的调用方恢复点。

与 **Call** 一样，某些调用约定会把 **Return** 的工作拆给调用方和被调用方分别完成。

## 协程

协程把 **Call** 和 **Return** 中的一部分步骤拆成三种独立操作，从而扩展了函数的能力：**Suspend（挂起）**、**Resume（恢复）**和 **Destroy（销毁）**。

**Suspend** 会在当前位置挂起协程，把控制权交还给调用方或恢复方，同时保留活动帧。挂起时仍在作用域内的对象也继续存活。

和函数只能从自身执行 **Return** 类似，协程也只能从自身内部、在明确定义的挂起点执行 **Suspend**。

**Resume** 从上次挂起的位置继续执行协程，并重新激活它的活动帧。

**Destroy** 不恢复协程，直接销毁其活动帧。挂起点仍在作用域内的对象会被销毁，活动帧占用的内存也随之释放。

### 协程活动帧

协程可以挂起而不销毁活动帧，因此活动帧的生命周期不再保证严格嵌套。它通常不能直接分配在栈上，可能需要放到堆上。

C++ 协程 TS 也允许一种优化：如果编译器能证明协程的生命周期严格包含在调用方的生命周期内，就可以从调用方的活动帧中为协程帧分配空间。编译器足够聪明时，很多场景都能因此避开堆分配。

协程活动帧中，有些数据必须跨越挂起期保存，有些只在协程执行时需要。例如，生命周期不跨越任何挂起点的变量可以放在栈上。

从逻辑上看，协程活动帧可以分成两部分：“协程帧”和“栈帧”。

协程帧保存挂起期间仍需存在的状态；栈帧只在协程执行时存在，协程挂起并把控制权交还给调用方或恢复方时，它就会被释放。

### Suspend 操作

**Suspend** 允许协程在函数中途挂起，并把控制权交还给协程的调用方或恢复方。

协程体中只有特定位置可以挂起。在 C++ 协程 TS 中，`co_await` 和 `co_yield` 关键字会引入挂起点。

协程到达挂起点后，先为将来的恢复做好准备：
* 把需要保留的寄存器值写入协程帧；
* 在协程帧中记录当前挂起点。之后执行 **Resume** 时据此找到恢复位置，执行 **Destroy** 时则据此判断哪些对象仍在作用域内、需要销毁。

这些准备完成后，协程便进入“已挂起”状态。

在控制权交还给调用方或恢复方之前，协程还有机会执行一段附加逻辑。这段逻辑可以取得协程帧的句柄，供以后恢复或销毁协程。

附加逻辑发生在协程进入“已挂起”状态之后，因此它可以安排协程恢复而不必额外同步。反过来，如果先安排恢复、再进入挂起状态，挂起和恢复之间就可能发生竞争，需要同步才能保证安全。后续文章还会详细讨论这一点。

此后，协程可以立即恢复并继续运行，也可以把控制权交还给调用方或恢复方。

如果选择交还控制权，协程活动帧中的栈帧部分会从栈上弹出并释放。

### Resume 操作

**Resume** 只能作用于当前处于“已挂起”状态的协程。

函数要恢复协程，效果上相当于“调用”到某次函数调用的中间。恢复方通过协程帧句柄确定具体要恢复哪一次调用，并执行句柄的 `void resume()` 方法；这个句柄由对应的 **Suspend** 操作提供。

和普通函数调用一样，`resume()` 会分配新栈帧，把调用方的返回地址存入其中，再把控制权转移给目标函数。

区别在于，它不会从函数入口开始执行，而会从上次挂起的位置继续。实现上，它从协程帧中加载恢复点并跳转过去。

协程再次挂起或运行结束时，`resume()` 返回，调用它的函数继续执行。

### Destroy 操作

**Destroy** 不恢复协程，直接销毁协程帧。

**这项操作只能作用于已挂起的协程**。

**Destroy** 和 **Resume** 的执行方式很相似：它会重新激活协程的活动帧，包括分配新栈帧，并保存 **Destroy** 调用方的返回地址。

不过，它不会跳回最后一个挂起点继续执行协程体，而会进入另一条代码路径。这条路径依次析构挂起点仍在作用域内的局部变量，再释放协程帧占用的内存。

和 **Resume** 一样，**Destroy** 也通过协程帧句柄确定具体的活动帧。调用句柄的 `void destroy()` 方法即可执行销毁；这个句柄同样由对应的 **Suspend** 操作提供。

### 协程的 Call 操作

协程的 **Call** 与普通函数调用很相似。从调用方看，两者没有区别。

普通函数要等运行结束才返回；协程则在到达第一个挂起点时就会让调用方恢复执行。

执行协程的 **Call** 时，调用方分配新栈帧，把参数和返回地址写入其中，再把控制权交给协程。这一段与普通函数调用完全相同。

协程首先在堆上分配协程帧，再把参数从栈帧复制或移动到协程帧，使参数能够活过第一个挂起点。

### 协程的 Return 操作

协程的 **Return** 与普通函数略有不同。

协程执行返回语句，也就是 TS 中的 `co_return` 时，会先把返回值保存到某处，具体位置可以由协程类型自定义；随后销毁仍在作用域内的局部变量，但不销毁参数。

把控制权交还给调用方或恢复方之前，协程同样有机会执行附加逻辑。

这段逻辑可以发布返回值，也可以恢复另一个正在等待结果的协程，具体行为完全可以自定义。

接着，协程或者执行 **Suspend**，让协程帧继续存活；或者执行 **Destroy**，销毁协程帧。

控制权随后按照 **Suspend** 或 **Destroy** 的语义交还给调用方或恢复方，活动帧中的栈帧部分也会从栈上弹出。

注意，传给 **Return** 的值与初始 **Call** 返回给调用方的值不是同一个概念。协程的 **Return** 可能发生在初始 **Call** 已经返回很久以后。

## 一段执行过程

下面用一个简单例子，把协程从调用、挂起到再次恢复的过程画出来。

假设函数（也可能是协程）`f()` 调用了协程 `x(int a)`。

调用发生前，内存和寄存器的状态大致如下：
```
STACK                     REGISTERS               HEAP

                          +------+
+---------------+ <------ | rsp  |
|  f()          |         +------+
+---------------+
| ...           |
|               |
```

调用 `x(42)` 后，系统先像调用普通函数那样为 `x()` 创建栈帧。
```
STACK                     REGISTERS               HEAP
+----------------+ <-+
|  x()           |   |
| a  = 42        |   |
| ret= f()+0x123 |   |    +------+
+----------------+   +--- | rsp  |
|  f()           |        +------+
+----------------+
| ...            |
|                |
```

随后，协程 `x()` 在堆上分配协程帧，并把参数复制或移动进去，得到下图所示的状态。编译器通常会用栈指针之外的另一个寄存器保存协程帧地址，例如 MSVC 会使用 `rbp`。
```
STACK                     REGISTERS               HEAP
+----------------+ <-+
|  x()           |   |
| a  = 42        |   |                   +-->  +-----------+
| ret= f()+0x123 |   |    +------+       |     |  x()      |
+----------------+   +--- | rsp  |       |     | a =  42   |
|  f()           |        +------+       |     +-----------+
+----------------+        | rbp  | ------+
| ...            |        +------+
|                |
```

如果协程 `x()` 接着调用普通函数 `g()`，状态会变成这样：
```
STACK                     REGISTERS               HEAP
+----------------+ <-+
|  g()           |   |
| ret= x()+0x45  |   |
+----------------+   |
|  x()           |   |
| coroframe      | --|-------------------+
| a  = 42        |   |                   +-->  +-----------+
| ret= f()+0x123 |   |    +------+             |  x()      |
+----------------+   +--- | rsp  |             | a =  42   |
|  f()           |        +------+             +-----------+
+----------------+        | rbp  |
| ...            |        +------+
|                |
```

`g()` 返回时会销毁自己的活动帧，并恢复 `x()` 的活动帧。假设 `g()` 的返回值被存入局部变量 `b`，而 `b` 位于协程帧中：
```
STACK                     REGISTERS               HEAP
+----------------+ <-+
|  x()           |   |
| a  = 42        |   |                   +-->  +-----------+
| ret= f()+0x123 |   |    +------+       |     |  x()      |
+----------------+   +--- | rsp  |       |     | a =  42   |
|  f()           |        +------+       |     | b = 789   |
+----------------+        | rbp  | ------+     +-----------+
| ...            |        +------+
|                |
```

如果 `x()` 此时到达挂起点，它会挂起但不销毁活动帧，控制权则回到 `f()`。

`x()` 的栈帧部分随之弹出，协程帧仍留在堆上。协程第一次挂起时会向调用方返回一个值，其中通常包含已挂起协程帧的句柄，以便以后恢复。`x()` 还会把恢复点地址写入协程帧，图中用 `RP` 表示。
```
STACK                     REGISTERS               HEAP
                                        +----> +-----------+
                          +------+      |      |  x()      |
+----------------+ <----- | rsp  |      |      | a =  42   |
|  f()           |        +------+      |      | b = 789   |
| handle     ----|---+    | rbp  |      |      | RP=x()+99 |
| ...            |   |    +------+      |      +-----------+
|                |   |                  |
|                |   +------------------+
```

此后，句柄可以像普通值一样在函数之间传递。过一段时间，某个函数（例如 `h()`）可能从另一条调用栈，甚至另一个线程中决定恢复协程。异步 I/O 完成就是一种常见触发条件。

负责恢复的函数调用 `void resume(handle)`。在调用方看来，这和调用任何接收一个参数、返回 `void` 的普通函数没有区别。

这次调用会创建新栈帧，记录 `resume()` 调用方的返回地址；随后把协程帧地址加载到寄存器以激活它，并从帧中记录的恢复点继续执行 `x()`。
```
STACK                     REGISTERS               HEAP
+----------------+ <-+
|  x()           |   |                   +-->  +-----------+
| ret= h()+0x87  |   |    +------+       |     |  x()      |
+----------------+   +--- | rsp  |       |     | a =  42   |
|  h()           |        +------+       |     | b = 789   |
| handle         |        | rbp  | ------+     +-----------+
+----------------+        +------+
| ...            |
|                |
```

## 总结

协程是函数的一种泛化。普通函数只有 **Call** 和 **Return** 两种操作，协程又增加了 **Suspend**、**Resume** 和 **Destroy**。

这五种操作构成了一套分析协程及其控制流的基本模型。
