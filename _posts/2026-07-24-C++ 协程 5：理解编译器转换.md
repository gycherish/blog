这些解释仍然跳过了一块重要细节。前文谈到“挂起点”时，只说“协程在这里挂起”“协程从这里恢复”，没有说明挂起究竟意味着什么，编译器又可能怎样实现它。

本文会把前面的概念串起来，逐步把一个协程降低成语义等价、不使用协程的命令式 C++ 代码，从而看清协程到达挂起点时发生的事。

这里不会复刻某个具体编译器生成机器码的准确过程，真实编译器还会使用其他技巧。本文展示的只是把协程降低成可移植 C++ 代码的一种可能方式。

## 问题设定

假设有一个基础 `task` 类型，它既是 Awaitable，也是协程返回类型。为了简化问题，这种协程只异步产生一个 `int` 结果。

本文会把下面的协程函数逐步降低成不含 `co_await`、`co_return` 等协程关键字的 C++ 代码：

```c++
// Forward declaration of some other function. Its implementation is not relevant.
task f(int x);

// A simple coroutine that we are going to translate to non-C++ code
task g(int x) {
    int fx = co_await f(x);
    co_return fx * fx;
}
```

## 定义 `task` 类型

先声明要使用的 `task` 类。

分析协程如何降低时，不需要知道这些方法的具体定义。转换过程只会插入对它们的调用。

方法本身并不复杂，可以把实现它们当成对前几篇文章的练习。

```c++
class task {
public:
    struct awaiter;

    class promise_type {
    public:
        promise_type() noexcept;
        ~promise_type();

        struct final_awaiter {
            bool await_ready() noexcept;
            std::coroutine_handle<> await_suspend(
                std::coroutine_handle<promise_type> h) noexcept;
            void await_resume() noexcept;
        };

        task get_return_object() noexcept;
        std::suspend_always initial_suspend() noexcept;
        final_awaiter final_suspend() noexcept;
        void unhandled_exception() noexcept;
        void return_value(int result) noexcept;

    private:
        friend task::awaiter;
        std::coroutine_handle<> continuation_;
        std::variant<std::monostate, int, std::exception_ptr> result_;
    };

    task(task&& t) noexcept;
    ~task();
    task& operator=(task&& t) noexcept;

    struct awaiter {
        explicit awaiter(std::coroutine_handle<promise_type> h) noexcept;
        bool await_ready() noexcept;
        std::coroutine_handle<promise_type> await_suspend(
            std::coroutine_handle<> h) noexcept;
        int await_resume();
    private:
        std::coroutine_handle<promise_type> coro_;
    };

    awaiter operator co_await() && noexcept;

private:
    explicit task(std::coroutine_handle<promise_type> h) noexcept;

    std::coroutine_handle<promise_type> coro_;
};
```

读过 [《理解对称转移》](/blog/posts/C++-协程-4-理解对称转移/) 后，这个 `task` 的结构应该很熟悉。

## 第 1 步：确定 Promise 类型

```c++
task g(int x) {
    int fx = co_await f(x);
    co_return fx * fx;
}
```

编译器发现函数包含 `co_await`、`co_yield` 或 `co_return` 中的任意一个，便启动协程转换。

第一步是确定协程使用的 `promise_type`。

做法是把函数签名中的返回类型和参数类型代入 `std::coroutine_traits` 的模板参数。

函数 `g` 返回 `task`，并接收一个 `int` 参数，因此编译器查找 `std::coroutine_traits<task, int>::promise_type`。

为方便后文引用，先定义别名：
```c++
using __g_promise_t = std::coroutine_traits<task, int>::promise_type;
```

**注意：本文用双下划线开头的名字表示编译器生成的内部符号。这类名字由实现保留，不应出现在用户代码中。**

这里没有特化 `std::coroutine_traits`，所以会实例化主模板。主模板把自身的 `promise_type` 定义为返回类型中同名嵌套类型的别名，本例最终解析为 `task::promise_type`。

## 第 2 步：创建协程状态

协程挂起时必须保留执行状态、参数和局部变量，之后恢复时才能继续使用。

C++ 标准把承载这些数据的对象称为**协程状态**（coroutine state），它通常分配在堆上。

先为协程 `g` 定义一个协程状态结构体。

此时还不知道完整布局，暂时留空。

```c++
struct __g_state {
  // to be filled out
};
```

协程状态包含：

* Promise 对象
* 任何函数参数的副本
* 当前挂起点，以及怎样恢复或销毁协程的信息
* 生命周期跨越挂起点的局部变量和临时对象

先加入 Promise 对象和参数副本所需的存储。

```c++
struct __g_state {
    int x;
    __g_promise_t __promise;

    // to be filled out
};
```

接着添加构造函数，初始化这些成员。

编译器会先尝试用各参数副本的左值引用构造 Promise；如果这个调用无效，再退回默认构造函数。

可以用一个简单的辅助函数表达这条规则：
```c++
template<typename Promise, typename... Params>
Promise construct_promise([[maybe_unused]] Params&... params) {
    if constexpr (std::constructible_from<Promise, Params&...>) {
        return Promise(params...);
    } else {
        return Promise();
    }
}
```

于是协程状态的构造函数大致如下：

```c++
struct __g_state {
    __g_state(int&& x)
    : x(static_cast<int&&>(x))
    , __promise(construct_promise<__g_promise_t>(this->x))
    {}

    int x;
    __g_promise_t __promise;
    // to be filled out
};
```

协程状态类型已经有了基本轮廓。下面开始降低 `g()`：先在堆上分配 `__g_state`，并传入函数参数，把它们复制或移动进协程状态。

先约定一个术语。本文把协程实现中负责初始化协程状态、准备启动协程的部分称为“ramp function”。它相当于进入协程体之前的入口坡道。

```c++
task g(int x) {
    auto* state = new __g_state(static_cast<int&&>(x));
    // ... implement rest of the ramp function
}
```

本例的 Promise 类型没有自定义 `operator new`，因此直接调用全局 `::operator new`。

如果 Promise 类型定义了自定义 `operator new`，则优先调用它。编译器先检查 `(size, paramLvalues...)` 参数列表是否可用，可用就传入协程参数的左值引用；否则只传 `(size)`。让 `operator new` 访问协程参数有时称为“parameter preview”，当分配器作为参数传给协程时尤其有用。

只要编译器找到 `__g_promise_t::operator new` 的定义，就会降低为下面的逻辑：
```c++
template<typename Promise, typename... Args>
void* __promise_allocate(std::size_t size, [[maybe_unused]] Args&... args) {
  if constexpr (requires { Promise::operator new(size, args...); }) {
    return Promise::operator new(size, args...);
  } else {
    return Promise::operator new(size);
  }
}

task g(int x) {
    void* state_mem = __promise_allocate<__g_promise_t>(sizeof(__g_state), x);
    __g_state* state;
    try {
        state = ::new (state_mem) __g_state(static_cast<int&&>(x));
    } catch (...) {
        __g_promise_t::operator delete(state_mem);
        throw;
    }
    // ... implement rest of the ramp function
}
```

这个 Promise 类型也没有定义静态成员 `get_return_object_on_allocation_failure()`。如果定义了，分配时会改用 `operator new` 的 `std::nothrow_t` 形式；返回 `nullptr` 时，ramp function 直接执行 `return __g_promise_t::get_return_object_on_allocation_failure();`。

也就是：
```c++
task g(int x) {
    auto* state = ::new (std::nothrow) __g_state(static_cast<int&&>(x));
    if (state == nullptr) {
        return __g_promise_t::get_return_object_on_allocation_failure();
    }
    // ... implement rest of the ramp function
}
```

后文为保持示例简洁，只保留调用全局 `::operator new` 的最简单形式。

## 第 3 步：调用 `get_return_object()`

ramp function 接下来调用 Promise 对象的 `get_return_object()`，取得自身要返回的值。

先把结果存入局部变量，等其他步骤完成后，在 ramp function 末尾返回。

```c++
task g(int x) {
    auto* state = new __g_state(static_cast<int&&>(x));
    decltype(auto) return_value = state->__promise.get_return_object();
    // ... implement rest of ramp function
    return return_value;
}
```

`get_return_object()` 可能抛异常，此时必须释放已经分配的协程状态。为稳妥起见，先让 `std::unique_ptr` 接管状态；后续操作抛异常时，它会自动释放内存：

```c++
task g(int x) {
    std::unique_ptr<__g_state> state(new __g_state(static_cast<int&&>(x)));
    decltype(auto) return_value = state->__promise.get_return_object();
    // ... implement rest of ramp function
    return return_value;
}
```

## 第 4 步：初始挂起点

调用 `get_return_object()` 后，ramp function 开始启动协程体。协程体的第一项操作就是初始挂起点，也就是求值 `co_await promise.initial_suspend()`。

最直观的实现，是先把协程视为已在初始位置挂起，再通过恢复它来启动协程。但初始挂起点在异常处理和协程状态生命周期上有一些特殊规则。这些规则来自 C++20 发布前的一次后期调整，用来修复此前发现的问题。

求值初始挂起点时，如果以下操作抛出异常：
* 调用 `initial_suspend()`；
* 调用返回对象的 `operator co_await()`，如果定义了该运算符；
* 调用 Awaiter 的 `await_ready()`；
* 调用 Awaiter 的 `await_suspend()`。

异常会传播给 ramp function 的调用方，协程状态自动销毁。

如果异常来自以下操作：
* 调用 `await_resume()`；
* 析构 `operator co_await()` 的返回对象，如果存在；
* 析构 `initial_suspend()` 的返回对象。

异常则由协程体捕获，并调用 `promise.unhandled_exception()`。

因此，这段转换要拆开处理：一部分位于 ramp function，另一部分位于协程体。

`initial_suspend()` 以及可选的 `operator co_await()` 所返回的对象都可能跨越挂起点：它们在挂起前创建，恢复后才销毁。因此，存储空间必须位于协程状态中。

本例的 `initial_suspend()` 返回 `std::suspend_always`，它是空的可平凡构造类型。逻辑上仍要在协程状态中保存其实例，下面会显式加入这块存储，以展示一般情况。

对象只在调用 `initial_suspend()` 时构造，所以需要一种能显式控制生命周期的数据成员。

先定义辅助类 `manual_lifetime`。它本身可平凡构造和析构，但允许在需要时显式构造或销毁存放其中的值。

```c++
template<typename T>
struct manual_lifetime {
    manual_lifetime() noexcept = default;
    ~manual_lifetime() = default;

    // Not copyable/movable
    manual_lifetime(const manual_lifetime&) = delete;
    manual_lifetime(manual_lifetime&&) = delete;
    manual_lifetime& operator=(const manual_lifetime&) = delete;
    manual_lifetime& operator=(manual_lifetime&&) = delete;

    template<typename Factory>
    requires std::invocable<Factory&> && std::same_as<std::invoke_result_t<Factory&>, T>
    T& construct_from(Factory factory) noexcept(std::is_nothrow_invocable_v<Factory&>) {
        return *::new (static_cast<void*>(&storage)) T(factory());
    }

    void destroy() noexcept(std::is_nothrow_destructible_v<T>) {
        std::destroy_at(std::launder(reinterpret_cast<T*>(&storage)));
    }

    T& get() & noexcept {
        return *std::launder(reinterpret_cast<T*>(&storage));
    }

private:
    alignas(T) std::byte storage[sizeof(T)];
};
```

`construct_from()` 接收 lambda，而非直接接收构造参数。这样用函数调用结果初始化变量时，可以利用保证的复制消除就地构造对象；若直接传构造参数，会多出一次不必要的移动构造。

现在用 `manual_lifetime` 为 `promise.initial_suspend()` 返回的临时对象声明成员。

```c++
struct __g_state {
    __g_state(int&& x);

    int x;
    __g_promise_t __promise;
    manual_lifetime<std::suspend_always> __tmp1;
    // to be filled out
};
```

`std::suspend_always` 没有 `operator co_await()`，因此不需要为运算符调用结果再保存一个临时对象。

调用 `initial_suspend()` 构造对象后，按 `co_await` 规则依次处理 `await_ready()`、`await_suspend()` 和 `await_resume()`。

调用 `await_suspend()` 时要传入当前协程的句柄。这里通过 `std::coroutine_handle<__g_promise_t>::from_promise()` 从 Promise 引用取得句柄，后文再实现其内部逻辑。

本例的 `.await_suspend(handle)` 返回 `void`，所以不必像返回 `bool` 或 `coroutine_handle` 的版本那样，再决定恢复当前协程还是另一个协程。

`std::suspend_always` Awaiter 的所有方法都是 `noexcept`，这里无需处理异常。若它们可能抛出，就要增加代码，保证异常离开 ramp function 前销毁临时 `std::suspend_always` 对象。

`await_suspend()` 成功返回，或者执行即将进入协程体时，协程状态已经不应在异常发生时自动销毁。此时对持有状态的 `std::unique_ptr` 调用 `release()`，避免 ramp function 返回时误删状态。

初始挂起表达式的前半部分可以写成：

```c++
task g(int x) {
    std::unique_ptr<__g_state> state(new __g_state(static_cast<int&&>(x)));
    decltype(auto) return_value = state->__promise.get_return_object();

    state->__tmp1.construct_from([&]() -> decltype(auto) {
        return state->__promise.initial_suspend();
    });
    if (!state->__tmp1.get().await_ready()) {
        //
        // ... suspend-coroutine here
        //
        state->__tmp1.get().await_suspend(
            std::coroutine_handle<__g_promise_t>::from_promise(state->__promise));

        state.release();

        // fall through to return statement below.
    } else {
        // Coroutine did not suspend.

        state.release();

        //
        // ... start executing the coroutine body
        //
    }
    return __return_val;
}
```

`await_resume()` 调用和 `__tmp1` 的析构发生在协程体中，不属于 ramp function。

初始挂起点的大部分求值逻辑已经具备，但 ramp function 中仍有几个 TODO。要补上它们，得先设计协程怎样记录挂起位置，以及之后怎样恢复。

## 第 5 步：记录挂起点

协程恢复时必须回到控制流中原先挂起的位置。

还要记录每个挂起点有哪些自动存储期对象仍然存活。若协程被销毁而非恢复，销毁路径要据此析构正确的对象。

一种实现方式是给每个挂起点分配唯一编号，并把当前编号存进协程状态的整型成员。

每次挂起前写入对应编号；恢复或销毁时读取编号，就知道该从哪条路径继续。

这不是唯一方案，但截至本文写作时的 2022 年，MSVC、Clang 和 GCC 都采用了类似方法。另一种可能方案是为每个挂起点保存独立的恢复函数和销毁函数指针，本文不展开。

为协程状态加入整型挂起点索引，并初始化为 0；本文固定用 0 表示初始挂起点。

```c++
struct __g_state {
    __g_state(int&& x);

    int x;
    __g_promise_t __promise;
    int __suspend_point = 0;  // <-- add the suspend-point index
    manual_lifetime<std::suspend_always> __tmp1;
    // to be filled out
};
```

## 第 6 步：实现 `coroutine_handle::resume()` 和 `coroutine_handle::destroy()`

`coroutine_handle::resume()` 最终要调用某个实现协程体的函数。该函数读取挂起点索引，再跳到控制流中的对应位置。

`coroutine_handle::destroy()` 要进入相应销毁路径，析构当前挂起点仍在作用域内的对象；`coroutine_handle::done()` 则查询当前是否停在最终挂起点。

`coroutine_handle` 的接口不知道具体协程状态类型，`coroutine_handle<void>` 可以指向_任意_协程实例，因此实现需要做类型擦除。

可以在协程状态中保存恢复函数和销毁函数的指针，让 `coroutine_handle::resume()`、`destroy()` 间接调用它们。

`coroutine_handle::address()` 和 `from_address()` 还要求句柄能与 `void*` 相互转换。

此外，指向同一协程的任意句柄都能恢复或销毁它，不限于最近一次传给 `await_suspend()` 的那个句柄。

综合这些要求，`coroutine_handle` 本身只保存协程状态指针，恢复和销毁函数指针则放在协程状态中。

句柄要能指向任意协程状态，所以这些函数指针成员在所有协程状态类型中必须有一致布局。

直接做法是让所有协程状态继承同一个基类，由基类保存这些成员。

例如定义：
```c++
struct __coroutine_state {
    using __resume_fn = void(__coroutine_state*);
    using __destroy_fn = void(__coroutine_state*);

    __resume_fn* __resume;
    __destroy_fn* __destroy;
};
```

`coroutine_handle::resume()` 只需调用 `__resume()`，传入 `__coroutine_state` 指针；`destroy()` 对 `__destroy` 做同样处理。

这里用空的 `__resume` 函数指针表示协程停在最终挂起点。这个约定很方便，因为最终挂起点不允许 `resume()`，只能 `destroy()`。若有人对停在最终挂起点的协程调用 `resume()`，本来就是未定义行为；实际会调用空函数指针，通常很快暴露错误。

据此实现 `coroutine_handle<void>`：
```c++
namespace std
{
    template<typename Promise = void>
    class coroutine_handle;

    template<>
    class coroutine_handle<void> {
    public:
        coroutine_handle() noexcept = default;
        coroutine_handle(const coroutine_handle&) noexcept = default;
        coroutine_handle& operator=(const coroutine_handle&) noexcept = default;

        void* address() const {
            return static_cast<void*>(state_);
        }

        static coroutine_handle from_address(void* ptr) {
            coroutine_handle h;
            h.state_ = static_cast<__coroutine_state*>(ptr);
            return h;
        }

        explicit operator bool() noexcept {
            return state_ != nullptr;
        }
        
        friend bool operator==(coroutine_handle a, coroutine_handle b) noexcept {
            return a.state_ == b.state_;
        }

        void resume() const {
            state_->__resume(state_);
        }
        void destroy() const {
            state_->__destroy(state_);
        }

        bool done() const {
            return state_->__resume == nullptr;
        }

    private:
        __coroutine_state* state_ = nullptr;
    };
}
```

## 第 7 步：实现 `coroutine_handle<Promise>::promise()` 和 `from_promise()`

`coroutine_handle<Promise>` 特化的大部分逻辑可以复用 `coroutine_handle<void>`。新增的能力是通过 `promise()` 访问协程状态中的 Promise 对象，以及从 Promise 引用构造句柄。

句柄不能依赖某个具体协程状态类型，因为 `coroutine_handle<Promise>` 必须能引用所有 Promise 类型恰好为 `Promise` 的协程状态。

因此再定义一个继承 `__coroutine_state`、并包含 Promise 存储的基类。所有使用同一 Promise 类型的具体协程状态都从它派生。

```c++
template<typename Promise>
struct __coroutine_state_with_promise : __coroutine_state {
    __coroutine_state_with_promise() noexcept {}
    ~__coroutine_state_with_promise() {}

    union {
        Promise __promise;
    };
};
```

这里把 `__promise` 声明在匿名联合体中，原因与构造顺序有关。

具体协程状态派生类中含有参数副本成员。C++ 默认先初始化基类成员，再初始化派生类成员。如果把 Promise 声明为普通基类成员，它会早于参数副本构造。

实际要求恰好相反：先构造参数副本，再构造 Promise，因为 Promise 构造函数可能接收这些副本的引用。

所以基类只为 Promise 保留存储，使它在所有协程状态中都位于固定偏移；实际构造和析构交给派生类，在参数副本初始化之后显式执行。把 `__promise` 放进联合体即可获得这种控制。

更新 `__g_state`，让它继承新基类。

```c++
struct __g_state : __coroutine_state_with_promise<__g_promise_t> {
    __g_state(int&& __x)
    : x(static_cast<int&&>(__x)) {
        // Use placement-new to initialise the promise object in the base-class
        ::new ((void*)std::addressof(this->__promise))
            __g_promise_t(construct_promise<__g_promise_t>(x));
    }

    ~__g_state() {
        // Also need to manually call the promise destructor before the
        // argument objects are destroyed.
        this->__promise.~__g_promise_t();
    }

    int __suspend_point = 0;
    int x;
    manual_lifetime<std::suspend_always> __tmp1;
    // to be filled out
};
```

Promise 基类定义完成后，就能实现 `std::coroutine_handle<Promise>`。

大部分方法与 `coroutine_handle<void>` 相同，只是把 `__coroutine_state` 指针换成 `__coroutine_state_with_promise<Promise>`。

新增部分只有 `promise()` 和 `from_promise()`。

* `promise()` 直接返回协程状态中 `__promise` 成员的引用；
* `from_promise()` 从 Promise 对象地址反推出协程状态地址，只需减去 `__promise` 成员的偏移量。

实现如下：
```c++
namespace std
{
    template<typename Promise>
    class coroutine_handle {
        using state_t = __coroutine_state_with_promise<Promise>;
    public:
        coroutine_handle() noexcept = default;
        coroutine_handle(const coroutine_handle&) noexcept = default;
        coroutine_handle& operator=(const coroutine_handle&) noexcept = default;

        operator coroutine_handle<void>() const noexcept {
            return coroutine_handle<void>::from_address(address());
        }

        explicit operator bool() const noexcept {
            return state_ != nullptr;
        }

        friend bool operator==(coroutine_handle a, coroutine_handle b) noexcept {
            return a.state_ == b.state_;
        }

        void* address() const {
            return static_cast<void*>(static_cast<__coroutine_state*>(state_));
        }

        static coroutine_handle from_address(void* ptr) {
            coroutine_handle h;
            h.state_ = static_cast<state_t*>(static_cast<__coroutine_state*>(ptr));
            return h;
        }

        Promise& promise() const {
            return state_->__promise;
        }

        static coroutine_handle from_promise(Promise& promise) {
            coroutine_handle h;

            // We know the address of the __promise member, so calculate the
            // address of the coroutine-state by subtracting the offset of
            // the __promise field from this address.
            h.state_ = reinterpret_cast<state_t*>(
                reinterpret_cast<unsigned char*>(std::addressof(promise)) -
                offsetof(state_t, __promise)
            );

            return h;
        }

        // Define these in terms of their `coroutine_handle<void>` implementations

        void resume() const {
            static_cast<coroutine_handle<void>>(*this).resume();
        }

        void destroy() const {
            static_cast<coroutine_handle<void>>(*this).destroy();
        }

        bool done() const {
            return static_cast<coroutine_handle<void>>(*this).done();
        }

    private:
        state_t* state_;
    };
}
```

恢复机制已经定义，可以回到 ramp function，初始化刚加入协程状态的函数指针成员。

## 第 9 步：降低 `co_await` 表达式

接下来降低 `co_await f(x)`。

先求值 `f(x)`，得到一个临时 `task`。

临时 `task` 要到语句末尾的分号处才销毁，而语句中间可能在 `co_await` 处挂起。它的生命周期跨越挂起点，必须存入协程状态。

对临时 `task` 求值 `co_await` 时，会调用 `operator co_await()`，得到临时 `awaiter`。这个对象同样跨越挂起点，也要存入协程状态。

给 `__g_state` 添加相应成员：
```c++
struct __g_state : __coroutine_state_with_promise<__g_promise_t> {
    __g_state(int&& __x);
    ~__g_state();

    int __suspend_point = 0;
    int x;
    manual_lifetime<std::suspend_always> __tmp1;
    manual_lifetime<task> __tmp2;
    manual_lifetime<task::awaiter> __tmp3;
};
```

随后更新 `__g_resume()`：初始化临时对象，再依次处理构成 `co_await` 其余语义的 `await_ready()`、`await_suspend()` 和 `await_resume()`。

`task::awaiter::await_suspend()` 返回协程句柄，因此要生成恢复该句柄所指协程的代码。

调用 `await_suspend()` 前还要把挂起点索引更新为 1，并在跳转表中加入对应项，保证恢复时回到正确位置。

```c++
void __g_resume(__coroutine_state* s) {
    // We know that 's' points to a __g_state.
    auto* state = static_cast<__g_state*>(s);

    // Generate a jump-table to jump to the correct place in the code based
    // on the value of the suspend-point index.
    switch (state->__suspend_point) {
    case 0: goto suspend_point_0;
    case 1: goto suspend_point_1; // <-- add new jump-table entry
    default: std::unreachable();
    }

suspend_point_0:
    state->__tmp1.get().await_resume();
    state->__tmp1.destroy();

    //  int fx = co_await f(x);
    state->__tmp2.construct_from([&] {
        return f(state->x);
    });
    state->__tmp3.construct_from([&] {
        return static_cast<task&&>(state->__tmp2.get()).operator co_await();
    });
    if (!state->__tmp3.get().await_ready()) {
        // mark the suspend-point
        state->__suspend_point = 1;

        auto h = state->__tmp3.get().await_suspend(
            std::coroutine_handle<__g_promise_t>::from_promise(state->__promise));
        
        // Resume the returned coroutine-handle before returning.
        h.resume();
        return;
    }

suspend_point_1:
    int fx = state->__tmp3.get().await_resume();
    state->__tmp3.destroy();
    state->__tmp2.destroy();

    // TODO: Implement
    //  co_return fx * fx;
}
```

局部变量 `int fx` 的生命周期不跨越挂起点，无需放进协程状态，作为 `__g_resume` 的普通局部变量即可。

`__g_destroy()` 的跳转表也要增加一项，处理协程停在此处时被销毁的情况。

```c++
void __g_destroy(__coroutine_state* s) {
    auto* state = static_cast<__g_state*>(s);

    switch (state->__suspend_point) {
    case 0: goto suspend_point_0;
    case 1: goto suspend_point_1; // <-- add new jump-table entry
    default: std::unreachable();
    }

suspend_point_0:
    state->__tmp1.destroy();
    goto destroy_state;

suspend_point_1:
    state->__tmp3.destroy();
    state->__tmp2.destroy();
    goto destroy_state;

    // TODO: Add extra logic for other suspend-points here.

destroy_state:
    delete state;
}
```

至此，这条语句已经实现：
```c++
int fx = co_await f(x);
```

但 `f(x)` 没有标记为 `noexcept`，可能抛出异常；`awaiter::await_resume()` 同样如此。

协程体抛异常时，编译器要捕获它，再调用 `promise.unhandled_exception()`，让 Promise 决定怎样处理。下面实现这条路径。

## 第 10 步：实现 `unhandled_exception()`

标准条款 [`[dcl.fct.def.coroutine]`](https://eel.is/c++draft/dcl.fct.def.coroutine)规定，协程的行为如同函数体被替换为：

```c++
{
    promise-type promise promise-constructor-arguments ;
    try {
        co_await promise.initial_suspend() ;
        function-body
    } catch ( ... ) {
        if (!initial-await-resume-called)
            throw ;
        promise.unhandled_exception() ;
    }
final-suspend :
    co_await promise.final_suspend() ;
}
```

`initial-await_resume-called` 分支已经在 ramp function 中单独处理，这里不用重复考虑。

调整 `__g_resume()`，在协程体外包一层 `try`/`catch`。

跳转到 `try` 块内正确位置的 `switch` 必须放在块内，因为 C++ 不允许用 `goto` 从外部跳进 `try` 块。

对 `await_suspend()` 返回句柄的 `.resume()` 调用则必须放在 `try`/`catch` 外。若恢复目标协程时抛出异常，不应由当前协程捕获，而要传播到恢复当前协程的那次 `resume()`。因此，先把句柄存入函数顶部声明的变量，再 `goto` 到 `try`/`catch` 外执行 `.resume()`。

```c++
void __g_resume(__coroutine_state* s) {
    auto* state = static_cast<__g_state*>(s);

    std::coroutine_handle<void> coro_to_resume;

    try {
        switch (state->__suspend_point) {
        case 0: goto suspend_point_0;
        case 1: goto suspend_point_1; // <-- add new jump-table entry
        default: std::unreachable();
        }

suspend_point_0:
        state->__tmp1.get().await_resume();
        state->__tmp1.destroy();

        //  int fx = co_await f(x);
        state->__tmp2.construct_from([&] {
            return f(state->x);
        });
        state->__tmp3.construct_from([&] {
            return static_cast<task&&>(state->__tmp2.get()).operator co_await();
        });
        
        if (!state->__tmp3.get().await_ready()) {
            state->__suspend_point = 1;
            coro_to_resume = state->__tmp3.get().await_suspend(
                std::coroutine_handle<__g_promise_t>::from_promise(state->__promise));
            goto resume_coro;
        }

suspend_point_1:
        int fx = state->__tmp3.get().await_resume();
        state->__tmp3.destroy();
        state->__tmp2.destroy();

        // TODO: Implement
        //  co_return fx * fx;
    } catch (...) {
        state->__promise.unhandled_exception();
        goto final_suspend;
    }

final_suspend:
    // TODO: Implement
    // co_await promise.final_suspend();

resume_coro:
    coro_to_resume.resume();
    return;
}
```

上面的代码还有一个错误。如果 `__tmp3.get().await_resume()` 抛出异常，在进入 `catch` 前必须先析构 `__tmp3` 和 `__tmp2`，当前代码没有做到。

不能简单地先捕获异常、调用析构函数，再重新抛出。这样析构发生时异常已经被“处理”，会改变析构函数中 `std::uncaught_exceptions()` 的观察结果；正常的异常展开期间，这个函数应返回非零值。

可以定义一个 RAII 辅助类，保证异常导致作用域退出时调用析构函数。

```c++
template<typename T>
struct destructor_guard {
    explicit destructor_guard(manual_lifetime<T>& obj) noexcept
    : ptr_(std::addressof(obj))
    {}

    // non-movable
    destructor_guard(destructor_guard&&) = delete;
    destructor_guard& operator=(destructor_guard&&) = delete;

    ~destructor_guard() noexcept(std::is_nothrow_destructible_v<T>) {
        if (ptr_ != nullptr) {
            ptr_->destroy();
        }
    }

    void cancel() noexcept { ptr_ = nullptr; }

private:
    manual_lifetime<T>* ptr_;
};

// Partial specialisation for types that don't need their destructors called.
template<typename T>
requires std::is_trivially_destructible_v<T>
struct destructor_guard<T> {
    explicit destructor_guard(manual_lifetime<T>&) noexcept {}
    void cancel() noexcept {}
};

// Class-template argument deduction to simplify usage
template<typename T>
destructor_guard(manual_lifetime<T>& obj) -> destructor_guard<T>;
```

借助这个类型，可以保证异常发生时销毁协程状态中的相应变量。

正常离开作用域时，也用它触发现有变量的析构函数。

```c++
void __g_resume(__coroutine_state* s) {
    auto* state = static_cast<__g_state*>(s);

    std::coroutine_handle<void> coro_to_resume;

    try {
        switch (state->__suspend_point) {
        case 0: goto suspend_point_0;
        case 1: goto suspend_point_1; // <-- add new jump-table entry
        default: std::unreachable();
        }

suspend_point_0:
        {
            destructor_guard tmp1_dtor{state->__tmp1};
            state->__tmp1.get().await_resume();
        }

        //  int fx = co_await f(x);
        {
            state->__tmp2.construct_from([&] {
                return f(state->x);
            });
            destructor_guard tmp2_dtor{state->__tmp2};

            state->__tmp3.construct_from([&] {
                return static_cast<task&&>(state->__tmp2.get()).operator co_await();
            });
            destructor_guard tmp3_dtor{state->__tmp3};

            if (!state->__tmp3.get().await_ready()) {
                state->__suspend_point = 1;

                coro_to_resume = state->__tmp3.get().await_suspend(
                    std::coroutine_handle<__g_promise_t>::from_promise(state->__promise));

                // A coroutine suspends without exiting scopes.
                // So cancel the destructor-guards.
                tmp3_dtor.cancel();
                tmp2_dtor.cancel();

                goto resume_coro;
            }

            // Don't exit the scope here.
            //
            // We can't 'goto' a label that enters the scope of a variable with a
            // non-trivial destructor. So we have to exit the scope of the destructor
            // guards here without calling the destructors and then recreate them after
            // the `suspend_point_1` label.
            tmp3_dtor.cancel();
            tmp2_dtor.cancel();
        }

suspend_point_1:
        int fx = [&]() -> decltype(auto) {
            destructor_guard tmp2_dtor{state->__tmp2};
            destructor_guard tmp3_dtor{state->__tmp3};
            return state->__tmp3.get().await_resume();
        }();

        // TODO: Implement
        //  co_return fx * fx;
    } catch (...) {
        state->__promise.unhandled_exception();
        goto final_suspend;
    }

final_suspend:
    // TODO: Implement
    // co_await promise.final_suspend();

resume_coro:
    coro_to_resume.resume();
    return;
}
```

现在，无论异常从哪里抛出，协程体都会正确销毁局部变量；异常逃出协程体时，也会调用 `promise.unhandled_exception()`。

`promise.unhandled_exception()` 本身也可能抛出，例如重抛当前异常，这种情况还要特殊处理。

此时协程要捕获异常，把自身标记为停在最终挂起点，再重新抛出。

`__g_resume()` 的 `catch` 块需要改成：
```c++
try {
  // ...
} catch (...) {
    try {
        state->__promise.unhandled_exception();
    } catch (...) {
        state->__suspend_point = 2;
        state->__resume = nullptr; // mark as final-suspend-point
        throw;
    }
}
```
`__g_destroy` 的跳转表也要新增一项：
```c++
switch (state->__suspend_point) {
case 0: goto suspend_point_0;
case 1: goto suspend_point_1;
case 2: goto destroy_state; // no variables in scope that need to be destroyed
                            // just destroy the coroutine-state object.
}
```

注意，这里的最终挂起状态不一定等同于 `co_await promise.final_suspend()` 对应的最终挂起点。

`promise.final_suspend()` 的 `co_await` 通常会创建额外临时对象，`coroutine_handle::destroy()` 必须销毁它们。若 `promise.unhandled_exception()` 自己抛出，这些临时对象根本没有创建，销毁路径自然不同。

## 第 11 步：实现 `co_return`

下一步实现 `co_return fx * fx;`。

这一步相对简单。

`co_return <expr>` 映射为：
```c++
promise.return_value(<expr>);
goto final-suspend-point;
```

因此直接把 TODO 替换为：
```c++
state->__promise.return_value(fx * fx);
goto final_suspend;
```

这一步就完成了。

## 第 12 步：实现 `final_suspend()`

最后一个 TODO 是 `co_await promise.final_suspend()`。

`final_suspend()` 返回临时的 `task::promise_type::final_awaiter`。它需要存入协程状态，并由 `__g_destroy` 销毁。

这个类型没有 `operator co_await()`，所以不需要再保存一个运算符调用结果。

它和 `task::awaiter` 一样，让 `await_suspend()` 返回协程句柄，因此要对返回句柄调用 `resume()`。

如果协程没有在最终挂起点保持挂起，协程状态会隐式销毁。因此，执行越过协程末尾时要删除状态对象。

最终挂起的全部逻辑都必须是 `noexcept`，这里无需处理子表达式抛出的异常。

先给 `__g_state` 加入数据成员。
```c++
struct __g_state : __coroutine_state_with_promise<__g_promise_t> {
    __g_state(int&& __x);
    ~__g_state();

    int __suspend_point = 0;
    int x;
    manual_lifetime<std::suspend_always> __tmp1;
    manual_lifetime<task> __tmp2;
    manual_lifetime<task::awaiter> __tmp3;
    manual_lifetime<task::promise_type::final_awaiter> __tmp4; // <---
};
```

最终挂起表达式的主体如下：
```c++
final_suspend:
    // co_await promise.final_suspend
    {
        state->__tmp4.construct_from([&]() noexcept {
            return state->__promise.final_suspend();
        });
        destructor_guard tmp4_dtor{state->__tmp4};

        if (!state->__tmp4.get().await_ready()) {
            state->__suspend_point = 2;
            state->__resume = nullptr; // mark as final suspend-point

            coro_to_resume = state->__tmp4.get().await_suspend(
                std::coroutine_handle<__g_promise_t>::from_promise(state->__promise));

            tmp4_dtor.cancel();
            goto resume_coro;
        }

        state->__tmp4.get().await_resume();
    }

    //  Destroy coroutine-state if execution flows off end of coroutine
    delete state;
    return;
```

最后更新 `__g_destroy`，处理新挂起点。
```c++
void __g_destroy(__coroutine_state* state) {
    auto* state = static_cast<__g_state*>(s);

    switch (state->__suspend_point) {
    case 0: goto suspend_point_0;
    case 1: goto suspend_point_1;
    case 2: goto suspend_point_2;
    default: std::unreachable();
    }

suspend_point_0:
    state->__tmp1.destroy();
    goto destroy_state;

suspend_point_1:
    state->__tmp3.destroy();
    state->__tmp2.destroy();
    goto destroy_state;

suspend_point_2:
    state->__tmp4.destroy();
    goto destroy_state;

destroy_state:
    delete state;
}
```

至此，`g()` 已经完整降低。

看起来全部完成了。

但还差一个问题。

## 第 13 步：实现对称转移和 noop 协程

上面对 `__g_resume()` 的实现仍有问题。

[上一篇《理解对称转移》](/blog/posts/C++-协程-4-理解对称转移/) 详细讨论过这个问题，需要背景可以先回看。

[标准条款 `[expr.await]`](https://eel.is/c++draft/expr.await)对怎样处理 `await_suspend` 返回协程句柄给出了一些提示：
> If the type of await-suspend is std​::​coroutine_­handle<Z>, await-suspend.resume() is evaluated.

> [Note 1: This resumes the coroutine referred to by the result of await-suspend. Any number of coroutines can be successively resumed in this fashion, eventually returning control flow to the current coroutine caller or resumer ([dcl.fct.def.coroutine]). —- end note]

这条注释不具规范约束力，但强烈暗示实现应通过尾调用恢复下一个协程，而非递归调用。若协程在循环中相互恢复，递归实现很容易让栈无限增长。

当前实现从 `__g_resume()` 内调用下一个协程的 `.resume()`，然后才返回。于是 `__g_resume()` 的栈帧要等下一个协程挂起并返回后才会释放。

真正的尾调用会先弹出当前栈帧、保留返回地址，再用 `jmp` 跳到下一个协程的恢复函数。

可移植 C++ 没有办法强制尾部位置的调用一定变成尾调用。因此，这个模型要让恢复函数真正返回，先释放栈空间，再由调用方恢复下一个协程。

下一个协程挂起时还可能要求恢复第三个协程，转移链可以任意长，所以调用方需要用循环持续恢复。

这种循环通常称为“蹦床循环”（trampoline loop）：协程先返回循环，再由循环“弹”到下一个协程。

把恢复函数的返回类型从 `void` 改成“指向下一个协程状态的指针”，`coroutine_handle::resume()` 就能在循环中继续调用该状态的 `__resume()` 函数指针。

先修改 `__resume_fn` 的签名：
```c++
struct __coroutine_state {
    using __resume_fn = __coroutine_state* (__coroutine_state*);
    using __destroy_fn = void (__coroutine_state*);

    __resume_fn* __resume;
    __destroy_fn* __destroy;
};
```

`coroutine_handle::resume()` 随之改成：
```c++
void std::coroutine_handle<void>::resume() const {
    __coroutine_state* s = state_;
    do {
        s = s->__resume(s);
    } while (/* some condition */);
}
```

循环应该在什么条件下结束？

这里需要 `std::noop_coroutine()`。

`std::noop_coroutine()` 是一个工厂函数，返回带空操作 `resume()` 和 `destroy()` 的特殊协程句柄。协程挂起并从 `await_suspend()` 返回 noop coroutine handle，表示转移链到此结束；最初恢复它的 `coroutine_handle::resume()` 应该返回调用方。

因此要实现 `std::noop_coroutine()`，并让 `coroutine_handle::resume()` 在 `__coroutine_state` 指向 noop coroutine state 时退出循环。

一种策略是定义静态的 `__coroutine_state` 实例，把它指定为 noop coroutine state。`std::noop_coroutine()` 返回指向该对象的句柄；判断句柄是否为 noop 时，只需比较状态指针与这个静态对象的地址。

先定义特殊的 noop coroutine state：
```c++
struct __coroutine_state {
    using __resume_fn = __coroutine_state* (__coroutine_state*);
    using __destroy_fn = void (__coroutine_state*);

    __resume_fn* __resume;
    __destroy_fn* __destroy;

    static __coroutine_state* __noop_resume(__coroutine_state* state) noexcept {
        return state;
    }

    static void __noop_destroy(__coroutine_state*) noexcept {}

    static const __coroutine_state __noop_coroutine;
};

inline const __coroutine_state __coroutine_state::__noop_coroutine{
    &__coroutine_state::__noop_resume,
    &__coroutine_state::__noop_destroy
};
```

再实现 `std::coroutine_handle<noop_coroutine_promise>` 特化。
```c++
namespace std
{
    struct noop_coroutine_promise {};

    using noop_coroutine_handle = coroutine_handle<noop_coroutine_promise>;

    noop_coroutine_handle noop_coroutine() noexcept;

    template<>
    class coroutine_handle<noop_coroutine_promise> {
    public:
        constexpr coroutine_handle(const coroutine_handle&) noexcept = default;
        constexpr coroutine_handle& operator=(const coroutine_handle&) noexcept = default;

        constexpr explicit operator bool() noexcept { return true; }

        constexpr friend bool operator==(coroutine_handle, coroutine_handle) noexcept {
            return true;
        }

        operator coroutine_handle<void>() const noexcept {
            return coroutine_handle<void>::from_address(address());
        }

        noop_coroutine_promise& promise() const noexcept {
            static noop_coroutine_promise promise;
            return promise;
        }

        constexpr void resume() const noexcept {}
        constexpr void destroy() const noexcept {}
        constexpr bool done() const noexcept { return false; }

        constexpr void* address() const noexcept {
            return const_cast<__coroutine_state*>(&__coroutine_state::__noop_coroutine);
        }
    private:
        constexpr coroutine_handle() noexcept = default;

        friend noop_coroutine_handle noop_coroutine() noexcept {
            return {};
        }
    };
}
```

更新 `coroutine_handle::resume()`，遇到 noop coroutine state 时退出。

```c++
void std::coroutine_handle<void>::resume() const {
    __coroutine_state* s = state_;
    do {
        s = s->__resume(s);
    } while (s != &__coroutine_state::__noop_coroutine);
}
```

最后把 `__g_resume()` 改为返回 `__coroutine_state*`。

只需修改签名，并把：
```c++
coro_to_resume = ...;
goto resume_coro;
```
替换为：
```c++
auto h = ...;
return static_cast<__coroutine_state*>(h.address());
```

最后在 `delete state;` 之后添加：
```c++
return static_cast<__coroutine_state*>(std::noop_coroutine().address());
```

## 最后一件事

还有一个空间优化：当前 `__g_state` 比实际需要的更大。

四个临时对象各自占一块存储，但其中一些生命周期并不重叠。前一个对象销毁后，可以让后一个对象复用同一块空间，从而缩小协程状态。

实现方式是在合适的位置使用匿名联合体。

四个临时对象的生命周期如下：
- `__tmp1` 只存在于 `co_await promise.initial_suspend();`；
- `__tmp2` 只存在于 `int fx = co_await f(x);`；
- `__tmp3` 也只存在于 `int fx = co_await f(x);`，其生命周期嵌套在 `__tmp2` 内；
- `__tmp4` 只存在于 `co_await promise.final_suspend();`。

`__tmp2` 和 `__tmp3` 的生命周期重叠，必须放在同一个结构体里，同时保留存储。

`__tmp1` 和 `__tmp4` 的生命周期互不重叠，可以与前面的结构体一起放进匿名 `union`，共享空间。

数据成员可以改成：
```c++
struct __g_state : __coroutine_state_with_promise<__g_promise_t> {
    __g_state(int&& x);
    ~__g_state();

    int __suspend_point = 0;
    int x;

    struct __scope1 {
        manual_lifetime<task> __tmp2;
        manual_lifetime<task::awaiter> __tmp3;
    };

    union {
        manual_lifetime<std::suspend_always> __tmp1;
        __scope1 __s1;
        manual_lifetime<task::promise_type::final_awaiter> __tmp4;
    };
};
```

`__tmp2` 和 `__tmp3` 现在嵌套在 `__s1` 中，对它们的引用要改成 `state->__s1.tmp2` 之类的形式，其他代码不变。

这样能让协程状态再节省 16 字节。`__tmp1` 和 `__tmp4` 虽是空类型，原布局仍会分别为它们保留存储并填充到指针大小；共享联合体后，这部分空间不再重复占用。

## 合并最终结果

原始协程函数是：
```c++
task g(int x) {
    int fx = co_await f(x);
    co_return fx * fx;
}
```

完整降低后变成：
```c++
/////
// The coroutine promise-type

using __g_promise_t = std::coroutine_traits<task, int>::promise_type;

__coroutine_state* __g_resume(__coroutine_state* s);
void __g_destroy(__coroutine_state* s);

/////
// The coroutine-state definition

struct __g_state : __coroutine_state_with_promise<__g_promise_t> {
    __g_state(int&& x)
    : x(static_cast<int&&>(x)) {
        // Initialise the function-pointers used by coroutine_handle methods.
        this->__resume = &__g_resume;
        this->__destroy = &__g_destroy;

        // Use placement-new to initialise the promise object in the base-class
        // after we've initialised the argument copies.
        ::new ((void*)std::addressof(this->__promise))
            __g_promise_t(construct_promise<__g_promise_t>(this->x));
    }

    ~__g_state() {
        this->__promise.~__g_promise_t();
    }

    int __suspend_point = 0;

    // Argument copies
    int x;

    // Local variables/temporaries
    struct __scope1 {
        manual_lifetime<task> __tmp2;
        manual_lifetime<task::awaiter> __tmp3;
    };

    union {
        manual_lifetime<std::suspend_always> __tmp1;
        __scope1 __s1;
        manual_lifetime<task::promise_type::final_awaiter> __tmp4;
    };
};

/////
// The "ramp" function

task g(int x) {
    std::unique_ptr<__g_state> state(new __g_state(static_cast<int&&>(x)));
    decltype(auto) return_value = state->__promise.get_return_object();

    state->__tmp1.construct_from([&]() -> decltype(auto) {
        return state->__promise.initial_suspend();
    });
    if (!state->__tmp1.get().await_ready()) {
        state->__tmp1.get().await_suspend(
            std::coroutine_handle<__g_promise_t>::from_promise(state->__promise));
        state.release();
        // fall through to return statement below.
    } else {
        // Coroutine did not suspend. Start executing the body immediately.
        __g_resume(state.release());
    }
    return return_value;
}

/////
//  The "resume" function

__coroutine_state* __g_resume(__coroutine_state* s) {
    auto* state = static_cast<__g_state*>(s);

    try {
        switch (state->__suspend_point) {
        case 0: goto suspend_point_0;
        case 1: goto suspend_point_1; // <-- add new jump-table entry
        default: std::unreachable();
        }

suspend_point_0:
        {
            destructor_guard tmp1_dtor{state->__tmp1};
            state->__tmp1.get().await_resume();
        }

        //  int fx = co_await f(x);
        {
            state->__s1.__tmp2.construct_from([&] {
                return f(state->x);
            });
            destructor_guard tmp2_dtor{state->__s1.__tmp2};

            state->__s1.__tmp3.construct_from([&] {
                return static_cast<task&&>(state->__s1.__tmp2.get()).operator co_await();
            });
            destructor_guard tmp3_dtor{state->__s1.__tmp3};

            if (!state->__s1.__tmp3.get().await_ready()) {
                state->__suspend_point = 1;

                auto h = state->__s1.__tmp3.get().await_suspend(
                    std::coroutine_handle<__g_promise_t>::from_promise(state->__promise));

                // A coroutine suspends without exiting scopes.
                // So cancel the destructor-guards.
                tmp3_dtor.cancel();
                tmp2_dtor.cancel();

                return static_cast<__coroutine_state*>(h.address());
            }

            // Don't exit the scope here.
            // We can't 'goto' a label that enters the scope of a variable with a
            // non-trivial destructor. So we have to exit the scope of the destructor
            // guards here without calling the destructors and then recreate them after
            // the `suspend_point_1` label.
            tmp3_dtor.cancel();
            tmp2_dtor.cancel();
        }

suspend_point_1:
        int fx = [&]() -> decltype(auto) {
            destructor_guard tmp2_dtor{state->__s1.__tmp2};
            destructor_guard tmp3_dtor{state->__s1.__tmp3};
            return state->__s1.__tmp3.get().await_resume();
        }();

        //  co_return fx * fx;
        state->__promise.return_value(fx * fx);
        goto final_suspend;
    } catch (...) {
        state->__promise.unhandled_exception();
        goto final_suspend;
    }

final_suspend:
    // co_await promise.final_suspend
    {
        state->__tmp4.construct_from([&]() noexcept {
            return state->__promise.final_suspend();
        });
        destructor_guard tmp4_dtor{state->__tmp4};

        if (!state->__tmp4.get().await_ready()) {
            state->__suspend_point = 2;
            state->__resume = nullptr; // mark as final suspend-point

            auto h = state->__tmp4.get().await_suspend(
                std::coroutine_handle<__g_promise_t>::from_promise(state->__promise));

            tmp4_dtor.cancel();
            return static_cast<__coroutine_state*>(h.address());
        }

        state->__tmp4.get().await_resume();
    }

    //  Destroy coroutine-state if execution flows off end of coroutine
    delete state;

    return static_cast<__coroutine_state*>(std::noop_coroutine().address());
}

/////
// The "destroy" function

void __g_destroy(__coroutine_state* s) {
    auto* state = static_cast<__g_state*>(s);

    switch (state->__suspend_point) {
    case 0: goto suspend_point_0;
    case 1: goto suspend_point_1;
    case 2: goto suspend_point_2;
    default: std::unreachable();
    }

suspend_point_0:
    state->__tmp1.destroy();
    goto destroy_state;

suspend_point_1:
    state->__s1.__tmp3.destroy();
    state->__s1.__tmp2.destroy();
    goto destroy_state;

suspend_point_2:
    state->__tmp4.destroy();
    goto destroy_state;

destroy_state:
    delete state;
}
```
