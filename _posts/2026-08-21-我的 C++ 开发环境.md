最近准备写源码解析系列，但写之前总得先交代下开发环境。

其实，如果单纯记录我的开发环境用了哪些工具，写起来可能很简单，参考价值也有限。我更想基于我这些年的行业经验来说清楚为何我选择了这些工具，因为这才是真正影响工具选型的原因，脱离约束谈工具好坏是没有意义的。

## 行业背景

我在灾备行业深耕多年。灾备其实包含两个层面的含义：备份和容灾。其中备份说白了就是把客户的数据完整地复制一份出去，一旦哪天数据损坏或者遭遇勒索，这份副本就是数据恢复的来源；容灾则更进一步，普通的备份只能保证你的数据有多份副本，恢复时也只是单纯地恢复数据本身，而容灾却可以在客户环境宕机后完整地恢复出相同的一套环境并替代原来的环境对外提供服务。

不论是备份还是容灾，整个灾备行业对运行的灾备软件的要求是非常高的。不同实现程度的程序对 RPO(Recovery Point Objective) 和 RTO(Recovery Time Objective) 的影响直接决定一套灾备软件的级别，进而决定你的软件的价值，这是实打实会影响收入的东西。

影响灾备软件的技术选型的因素非常多，我这里只列举跟本文最相关的几条：

### 低资源占用率

这里并不是说灾备软件的 CPU/内存/IO 等指标一定要尽可能低，而是在完成同等任务的条件下尽可能地低。因为负责备份的程序是运行在客户机器上的，它在备份时不可避免地要和客户业务系统上的其他进程争抢资源。越低的资源占用意味着对客户端系统的影响就越低。资源占用率的高低甚至会直接作为投标的参数写进标书中。

### 高性能

这是我认为最重要的一条。对于财大气粗的客户，他们的环境起步几十个 CPU 核心、上百 GiB 内存、标配 NVMe 的固态硬盘，灾备程序多吃点资源对他们来说并不是很重要。但是性能永远是第一位的。想象一下，客户动辄几十 TB 甚至 PB 级别的数据让你开发的程序来进行备份。这可不是一次简单的文件拷贝，一份数据从客户的磁盘走到备份存储上，中间要经过读文件(磁盘)、压缩、加密等多道工序。如果别人家的程序需要几个小时就能做完一次全量备份，而你的程序需要一天，结果会怎样？显然客户不会选择你的程序。而且性能是会直接影响 RPO 和 RTO 指标的。

### 跨平台

这既是客户的要求也是我们自己的要求，毕竟客户的业务可能是特定的操作系统，而我们的产品不可能只卖给一个客户。而且，客户涉及各行各业，他们的业务系统更是千差万别。截至今天，我们都需要支持 Windows 最低版本到 Windows Server 2003(桌面版对应到 XP)，而 Linux 最低要支持到 RedHat 4，而且 Linux 的发行版更是多得数不胜数，常用的如 RedHat/Ubuntu/SUSE/UOS/openEuler... 等都要做适配。另外，还要适配不同的 CPU 架构，典型的如 x86_64/aarch64/loongarch64。

## 对开发环境的影响

### 编程语言

虽然我是做 C++ 开发的，但是撇开我的方向不说，灾备系统的底层组件也应该选择 C++ 来做。目前主打高性能的编程语言也就 C/C++/Rust/Zig 能真正够得上门槛（带 GC 的 Go/Java 就先靠边站）。C 作为面向过程的编程语言写复杂的程序比 C++ 更难；Rust 号称内存安全且高性能，但调用 Win32/POSIX 系统 API 得先写一层绑定，并且它支持不了过低的操作系统；至于 Zig，还未成年，就不折腾了。因此，在我看来 C++ 几乎是唯一选择。目前就连最火的 AI，其底层的基础设施几乎都是 C++ 写的，人们虽然 Python 用得很欢，但是没了 C++，PyTorch 都跑不起来。

### 编译工具链

这个是受跨平台因素影响的。目前 Windows 官方工具链已经停止对 XP 系统的支持了。官方的 Visual Studio 2017 是最后一个支持 XP 的版本，并且需要搭配 v141_xp 工具链：

![Windows XP Toolset](win-xp-toolset.png)

而 RedHat 4 对应的 Linux 内核/glibc 版本/gcc 版本也非常低。要想写出能编译运行在这些平台上的代码，工具链的选择非常重要，而这也会直接影响可用的 C++ 语言标准。

### 构建系统

C++ 构建系统的生态一直非常割裂，市面上存在着各种不同的构建系统: CMake/XMake/Meson/Bazel...，这些构建系统都各有特色。构建系统的选择也同样受到跨平台因素的影响。

随构建系统一起考虑的一般还有包管理，大型 C++ 项目不可避免地会依赖很多三方库，如何优雅地管理这些三方库，并能够对不同平台上的编译 BUG 打补丁就非常重要了，毕竟手搓可不是个好主意。

### 编辑器/IDE

同样的，这也受跨平台的影响。比起像 Visual Studio 这种强大但平台专属的 IDE，选择一款能够提供统一的开发、调试体验的编辑器/IDE 来进行日常开发就更重要了。

### 辅助工具

这一部分是最能够自由选择的，一般不会受运行环境的影响，毕竟只要核心代码编译通过，其他部分如格式化、静态分析、动态分析等工具是可以采用最新的。

## 我之前的开发环境

作为开发者，基于上面的简单分析可以知道，跨平台(特别是最低支持的平台)是对开发环境影响最大的因素。为了让公司的产品能运行在那么多的平台上，从一开始我们就做了一个很保守的方案：

- C++ 标准：C++98，不支持任何现代 C++ 特性。
- 编译工具链：Linux 基于 GCC 4.8.3 作为主力工具链（CentOS 7），没有开启 C++11 特性使得该工具链编译过的代码一般能直接在更低版本的 Linux 系统上编译通过；Windows 直接使用 Visual Studio 2008 (Windows Server 2008)进行编译。
- 构建系统：CMake 作为 C++ 构建系统事实上的标准显然是最佳选择；包管理通过 XRepo 辅助解决。
- 编辑器/IDE: 使用 VSCode 作为主力编辑器，配合其插件生态打造出适合开发 C++ 程序的 IDE。

## 痛苦与抉择

说实话，这几年为了开发环境没少折腾，整个过程非常痛苦：

你能想象没有现代 C++ 特性的 C++ 代码写起来有多麻烦吗？线程/互斥锁等基础设施要依赖老旧的 boost；没有 lambda 要额外定义全局或成员函数进行辅助；没有移动语义要么接受深拷贝，要么传指针或引用，为了降低生命周期管理的复杂度甚至使用智能指针(也是依赖老旧的 boost)；最痛苦的是没有协程，异步回调满天飞，本来一个函数就能搞定的事，为了维护生命周期不出问题，必须要额外定义一个类来持有状态；没有结构化并发，你的异步回调飞到哪里了都不好掌控；更重要的是 BUG 会只多不少...

你能想象天天在 CentOS 7/Windows Server 2008 上面开发、编译、调试的感觉吗？CentOS 7 已经停止维护了，相关的软件源也几乎都没了，想用的工具下载不了，要么用 Everything 的 ISO 自建，要么单独从外部下载；VSCode 也不再支持 CentOS 7 了，为了能继续使用只能编译高版本 glibc 并通过 patchelf 为 VSCode 的服务端指定解释器(ld-linux.so)和 rpath；Visual Studio 2008 那种古老的立体感的风格也很让人不舒服，会让我想起大学时用过的 VC6；其他所有相关的工具都会因为开发环境版本低而不得不使用老旧的工具，甚至无法使用。

你能想象运行环境因自带软件版本过低而无法 SSH 连接和拉取代码的痛苦吗？为了确保开发环境上编译的程序没问题，我们需要额外搭建与客户环境一致的运行环境用来做发包前编译打包，但是个人开发机的 SSH 版本较高，SSH 握手时直接失败，虽然可以显式指定算法来解决，但是依然很麻烦；更重要的是太低版本的 Linux 根本没有 Git/SVN，导致代码没法直接从仓库拉取，只能选择打包源码并拷贝过去，如果测试出 BUG 了，相关的修改还需要以手搓的形式提交到代码仓库。

类似的问题还有很多，就不一一举例了。

为了解决这些问题，有两种选择：

1. 不再支持客户那些老旧的运行环境
2. 升级编译工具链

方案 1 显然不合适，没有一家企业会为了内部开发的问题而选择放弃客户。那就只剩方案 2 了。为了能在升级编译工具链的情况下还能继续支持那些老旧的运行环境，我折腾了很久，具体不再细说，我直接给出方案：

### Windows 平台解决方案

考虑到官方的工具链是明确不支持的，因此为了使用最新的工具链只能想其他办法，好在市面上有现成的解决方案：[Mingw-w64](https://www.mingw-w64.org/) 项目。Mingw-w64 是 Windows 系统上的完整的运行时环境。通过它，我们可以脱离官方的 Visual Studio 并完全使用开源工具链开发出运行在 Windows 系统上的程序。

很多人以为 Mingw-w64 只是提供一层仿真层，其实不然，Mingw-w64 是实实在在的 Windows 下的 Native 的编译工具链，中间没有任何指令翻译，没有任何系统调用的转换。使用 Mingw-w64 不影响直接调用 Win32 API，编译出来的是纯正的 Win32 应用程序。甚至有些 C/C++ 运行时库中的实现比官方的更高效，Mingw-w64 编译生成的二进制在某些条件下甚至更快。

真正有 API 转换的是 [Cygwin](https://www.cygwin.com/)，你可以直接将 POSIX 平台相关的代码在 Windows 上几乎不做修改就能编译成 Win32 应用程序，但应用程序强制依赖 cygwin1.dll，该 dll 负责运行时的 API 转换。类似的，POSIX 平台下也有能运行 Windows 程序的项目，即 [Wine](https://www.winehq.org/)，不过它不直接负责编译，而是让 Win32 应用程序能在 POSIX 上运行。

Mingw-w64 项目虽然能完美符合我的需求，但是它也有个很明显的缺点，即它对 Win32 API 的封装并不完整。当然，这也是完全能够理解的，一方面 Win32 API 数量特别庞大，而 Mingw-w64 作为开源项目，很难抽出人力来完整覆盖所有细节；另一方面，大部分 Win32 API 其实使用场景并不多，没必要为了小众的需求浪费维护者的精力。当然，还有一个重要的点在于，Mingw-w64 项目完全依赖系统自带的 C 运行时，它提供的系统头文件只负责声明数据结构，并不会直接修改底层 ABI，只要头文件中的内容和官方的 Win32 API 对应得上，编译出的程序就不会有问题。这意味着，如果 Mingw-w64 提供的系统头文件存在数据结构定义错误的情况，你只需要跟官方的核对并修复后重新编译即可，即修复成本只是更改头文件的成本。我之前就为该项目修改过 iSCSI 相关的头文件，有兴趣的可以参考我提交的[修复 iSCSI 头文件的 PR](https://sourceforge.net/p/mingw-w64/mingw-w64/merge-requests/30/)。遗憾的是，官方从不合并这些 PR，再加上我的修改也不完整，后续就没管它了。

除了 Mingw-w64，还有一个项目，即 [YY-Thunks](https://github.com/Chuyu-Team/YY-Thunks) 通过抹平不同版本 Windows 系统的 Win32 API 差异也一定程度上解决了这个问题，有兴趣的读者可以自行了解，本文不再详述。

#### Mingw-w64 工具链选择

值得特别强调的是，Mingw-w64 项目实际上只提供运行时环境，简单理解就是对 Win32 C 运行时库和系统 API 的 Wrapper，并不提供编译工具链本身。只不过这套环境让市面上的开源工具链运行在 Windows 上成为了可能。当然，这也需要那些工具链本身提供对 Windows 的支持，所有这一切都离不开开源社区的紧密配合。

不过，Mingw-w64 官方确实也提供了预编译的基于 GCC 的工具链。实际上，其他开源社区还提供了基于 LLVM 的工具链。那么，这些工具链该如何选择呢？在选择之前需要先列举出影响工具链的因素：

| 项 | 作用 | 说明 |
|----|---------|---------|
| CPU 架构 | 决定程序能运行在什么硬件上 | Windows 下目前主要支持 x86/x64/aarch64 架构 |
| Win32 核心 ABI | 直接决定编译的程序能否在 Windows 系统上运行   | 比如 PE 格式，调用约定等，各家编译器必须遵守  |
| C 运行时 ABI | 对外提供 C 接口 | Windows 官方目前存在两套 C 运行时库，分别为 msvcrt 和 ucrt，由 Mingw-w64 项目提供编译配置 |
| C++ 运行时 ABI | 对外提供 C++ 接口 | 主要影响是异常处理机制：sjlj/dwarf/seh，由编译器提供编译配置 |
| 线程模型 | 对外提供线程功能支持 | 直接影响 C++ 标准库中的线程功能，主要有 win32/posix/mcf 三种模型， 由编译器提供编译配置，但是线程是系统提供的功能，能否使用还依赖其他组件|
| 工具链本身 | 提供编译能力 | 目前市面上开源的主要是 GCC 和 LLVM |

其中 Win32 核心 ABI 稳定不变，也可以不参与组合。剩下五项的不同组合直接影响编译出的 Win32 下的库文件和可执行程序具有不同的 ABI，不能互相兼容（比如 GCC 编译的程序不能链接 LLVM 编译的库），也直接影响编译出来的 Win32 应用程序能运行在什么版本的 Windows 系统上。下面对上述重点项目做进一步的解释。

**msvcrt/ucrt**：

|  项 | 说明 |
|---- | ---- |
| msvcrt |  msvcrt 作为 Windows 老牌 C 运行时，从 Windows 95 开始便作为系统的预装组件了。而且 Windows 为了兼容性，直到现在，最新版的 Windows 11 也依然预装。因此，如果你的程序想运行在更低的 Windows 系统上，比如 Windows Server 2003，那么 msvcrt 是必选项。不过 msvcrt 的缺点很明显，对 C 标准的支持较差，性能也一般，不过好在 Mingw-w64 弥补了一部分。 |
| ucrt | Windows 官方重写的更现代的 C 运行时库，功能更全、性能更优。只不过其只在 Windows 10 以后的版本才随系统发布。如果你的程序只考虑运行在 Windows 10 及更新的系统上，优选 ucrt。当然更低些的系统通过升级补丁包加安装 vcredist 也能使用 ucrt，只是会很麻烦。|

**sjlj/dwarf/seh**:

|  项 | 说明 |
|---- | ---- |
| sjlj | 通过 setjmp/longjmp 处理异常，非常老旧，且性能很差，基本已经被废弃，绝大部分情况可以不考虑。但其兼容性最好，且同时支持 32 位和 64 位平台，特殊情况下可以考虑。 |
| dwarf | 基于调试信息表处理异常，符合 C++ 的零开销抽象原则。缺点是只支持 32 位平台。但考虑到 GCC 和 LLVM 在 32 位平台上都只支持 sjlj 和 dwarf，而 sjlj 性能较差，因此，当你的程序运行在 32 位平台时，dwarf 几乎是必选项。 |
| seh | 结构化异常处理机制，Windows 环境原生支持，且在不抛出异常时性能最佳。因此，当你的程序运行在 64 位平台时，请无脑选 seh。|

**win32/posix/mcf**:

|  项 | 说明 |
|---- | ---- |
|win32 | 这里其实有新旧之分，旧 win32 是 GCC gthread 依赖的那一套东西，封装了少量的 Win32 API，缺少完整的 C++11 线程功能支持，但是兼容性很好。新 win32 类似，但是利用 Vista 及之后 Windows 系统新的内核特性实现了完整的 C++11 线程功能。二者都没有额外依赖，只是直接调用 win32 API 来实现的，如 CreateThread。GCC 13 之后 libstdc++ 中的线程功能支持使用新 win32 线程模型。LLVM 的 libc++ 原生支持新 win32。|
|posix| Windows 下的 POSIX 线程 API，如 pthread_create。但是需要依赖 libwinpthread。GCC 的 libstdc++ 的线程功能原生支持。 |
|mcf | 用于替代 posix 线程模型，为 GCC 的 libstdc++ 提供性能更优的线程功能。但是需要依赖 mcfgthread，且 mcf 官方最低只支持到 Windows 7。 | 

根据上述内容，我们可以总结出一套完整的选择矩阵(组合方式太多，只列出重要的组合)：

| 编译器 | CPU 位数 | 最低支持的 Windows 系统 | 选择 | 性能优化 | 
| ----- | -------- | ---------------------- | --- | --- |
| GCC | 32 位 | XP/Windows Server 2003 | msvcrt/dwarf/posix | - |
| GCC | 64 位 | XP/Windows Server 2003 | msvcrt/seh/posix | - |
| GCC | 64 位 | Windows 7/Windows Server 2008 R2 | msvcrt/seh/win32 | 追求极致性能：win32 -> mcf |
| GCC | 64 位 | Windows 10/Windows Server 2016 | ucrt/seh/win32 | 追求极致性能：win32 -> mcf |
| Clang(LLVM) | 32 位 | Windows 7/Windows Server 2008 R2 | msvcrt/dwarf/win32 | - |
| Clang(LLVM) | 64 位 | Windows 7/Windows Server 2008 R2 | msvcrt/seh/win32 | - |
| Clang(LLVM) | 64 位 | Windows 10/Windows Server 2016 | ucrt/seh/win32 | - |

这里必须要强调一点，其实上面的表格撒了谎。Mingw-w64 官方预编译的最新的工具链已经在很久之前就不再支持 XP 了，核心原因是 libwinpthread 引入了 Vista 才有的 API，如 `GetTickCount64`。[Mingw-w64 编号为 814 的 BUG](https://sourceforge.net/p/mingw-w64/bugs/814/) 说明了原因："The compiler does not work on Windows XP because libwinpthread-1 is compiled for using GetTickCount64()"。

当然，这不是说就不能支持 XP 了，只不过会更折腾一些。好在 [w64devkit](https://github.com/skeeto/w64devkit) 项目还在维护支持 XP 的最新工具链，只不过仅支持 32 位版本(其实 32 位版本的 XP 才是主流，而且 32 位程序可以跑在 64 位系统上，因此，只支持 32 位的已经足够了)。

有了上述对比，当面对 Mingw-w64 提供的 [GCC 工具链](https://github.com/niXman/mingw-builds-binaries/releases) 时就能根据自己的需求做出正确的选择了：

![Mingw GCC Toolchain](mingw-gcc.png)

目前 Mingw-w64 只提供基于 GCC 的工具链，基于 LLVM 的以及更多的组合方式的工具链可以去 [Mingw-w64 download](https://www.mingw-w64.org/downloads/) 下面找。比较经典的是直接选择 [MSYS2](https://www.msys2.org/) 提供的预编译好的工具链，而且 MSYS2 项目还基于 Cygwin 项目提供了一整套 Shell 环境。

对于那些爱折腾的，可以像我一样亲自通过交叉编译定制自己的工具链，感兴趣的可以参考我的[交叉工具链](https://gitee.com/gycherish/cross-toolchain) 的实现。不过，我已经很久没维护了，但是核心的编译流程和编译命令依然可直接使用。

至此，通过 Mingw-w64，我们就可以使用最新的 C++ 标准，最新的开发工具来编译能够运行在最低支持到 XP/Windows Server 2003 及以上系统上的程序了（我已经通过 C++23 编译的程序做过验证了）。

### POSIX 平台解决方案

POSIX 平台比 Windows 平台要麻烦很多，本文以 Linux 为例。[基于 Linux 内核的发行版](https://upload.wikimedia.org/wikipedia/commons/1/1b/Linux_Distribution_Timeline.svg) 多如牛毛：

![Linux Distro Timeline](linux-distro-timeline.png)

对于那些守规矩(不破坏兼容性)的发行版还好，遇到不守规矩(最典型的就是国产的发行版！)的，直接导致你的程序运行时出现稀奇古怪的问题，甚至直接 break 内核 API 和 ABI，导致你的驱动和应用层代码要针对性地打补丁。多余的牢骚就不再说了，总归最终也能解决问题，因此这一部分本文也不再讨论。

好在市面上大部分 Linux 发行版，著名的有 Debian 和 RedHat 两大分支，都不会轻易 break 内核，兼容性也是他们很看重的东西。那么，基于 Linux 内核良好的向后兼容性，以及 Linux 下 glibc 良好的向后兼容性，这为我们在 Linux 平台寻找解决方案带来了可能。但是这里要分两种情况考虑：

#### Linux 内核和 glibc 版本特别低

比如 RedHat 4 使用的 2.6.9 内核和 glibc 2.3.4。这种情况升级编译器非常困难，因为高版本编译器的实现本身会依赖更高版本的 C 和 C++ 标准库。而且高版本编译器语法检查更严格，如果让它搭配这么低的 glibc 头文件，根本就不可能编译。

针对这种情况，显然无法在目标平台上进行编译了，且不能使用 glibc，剩下的方案就是选择其他的 libc。好在开源社区提供了替代，因此针对该情况的解决方案为：

- 使用 [musl libc](https://musl.libc.org/) 替代 glibc。
- 在更高版本的开发机上交叉编译出运行在目标环境的程序（只要 [target triplet](https://wiki.osdev.org/Target_Triplet) 不同，即使 CPU 架构、内核版本完全相同依然算是交叉编译而不是本地编译）。

通过 musl libc 加上交叉编译虽然稍微麻烦一些，但是可以完美解决这种情况。针对 musl libc 的交叉工具链我在上文提到的我的交叉工具链的仓库中也有，可以一键编译生成相关工具链。

musl libc 还有两个重要特点：

1. 不吃 Linux 内核头文件：musl libc 自带了需要用来满足实现 C 标准库和 POSIX 标准所需要所有 Linux 内核结构的定义。而且官方只要求满足 [**conformant behaviour** 需要的最低版本内核](https://wiki.musl-libc.org/supported-platforms) 不低于 2.6.39。而且真的低了点也能用，官方的说法是低于该版本的内核依然可以运行，只是会有不同程度的不合规，应付 RedHat 4 的 2.6.9 版本是没问题的。也因此，我们可以永远搭配最高版本的 Linux 内核头文件来使用 musl libc，只要用户程序不显式调用高版本内核的 API，我们的程序就能跑在低版本 Linux 系统上。
2. 支持静态链接：相比 glibc 为动态链接而设计（好像也能静态链接，但是官方和社区都不建议，坑特别多，写大型项目一定不要这样做，我们可以单纯认为 glibc 不支持静态链接即可！），musl libc 完整支持静态链接，这意味着你的程序编译完可以像 go 程序那样，一个二进制随便丢到对应的系统上就能直接运行。插一句嘴：go 语言其实相当于自己实现了 libc，自己对内核做了适配，除了依赖内核不会再依赖任何其他系统的运行时库，所以才能做到静态链接。

不过，很多人对使用 musl libc 有个最大的担忧就是性能问题。其实大可不必，根据我的经验，musl libc 的性能完全没有问题：一方面其内部针对 POSIX 接口的实现大部分都只是直接对接内核 API，并没有明显的性能损失，甚至有些 API 比臃肿的 glibc 更高效；另一方面其最被大家诟病的 malloc 的实现的设计是可插拔的，即用户完全可以换成更高性能的实现，比如我的交叉工具链仓库就为 musl libc 适配了 [jemalloc](https://jemalloc.net/)。

考虑到使用 musl libc 需要交叉编译，后续有时间我会再写一篇交叉编译相关的文章。

#### Linux 内核和 glibc 版本适中

比如刚退休没多久的 RedHat 7，其内核是 3.10，glibc 是 2.17，基于该版本可以轻松升级编译器到最新版，目前这个版本也是 [manylinux](https://github.com/pypa/manylinux) 项目使用的基础版本（对应 manylinux2014，社区目前正在向基于 glibc 2.28 的 manylinux_2_28 迁移），几乎所有 python 在 Linux 下的包构建在这个版本之上，这也是为何 python 可以跨几乎所有平台的原因（Windows 当然更简单）。

不过，即使可以在目标机器升级编译器，但是考虑到目标平台其他工具老旧，一般也不建议直接在目标平台上编译。可以像 musl libc 那样，使用交叉工具链。好消息是，我们不必像 musl libc 那样大概率需要自己编译交叉工具链，基于 glibc 2.17 的工具链则有现成的：即 manylinux 项目提供的版本。

那么，怎么使用这个工具链呢？我之前在 [DeepSeek Harness 初体验](/blog/posts/DeepSeek-Harness-初体验/) 这篇文章中提到一款工具，即 [Pixi](https://pixi.prefix.dev/)，该工具管理的运行环境中就有基于 glibc 2.17 的 sysroot，可以搭配最新的 GCC16 使用。后续在源码分析系列文章中我会演示如何使用这个工具链。

### 其他方案

这里简单再介绍下其他方案：

- 使用 docker：完美隔离宿主系统的 sysroot，这是升级 glibc 的最佳途径。
- 使用其他编程语言：比如 go，本地编译和交叉编译就简单很多，还是静态链接。
- 使用 zig cc: zig cc 也能够编译 C++ 代码，并且可以不依赖系统 libc。

但是，不管哪种方案都有不完美的地方，建议大家根据需求来。另外，不想浪费生命，请远离 C++！

### 特别说明

- 无论 Windows 平台还是 Linux 平台当你选择了最低的系统版本的同时也意味着你的代码需要针对系统不同版本的 API 做适配。如果你调用了高版本的系统 API，显然也是无法运行在低版本系统之上的。
- 对于依赖较少的程序而言，上述方案可以轻松满足需求，但是大型项目从来不是单打独斗，因此你的代码能否真的运行在较低版本的系统之上，还取决于你所依赖的众多三方库的适配情况。好在，大部分三方库只吃 C++ 标准库版本，除非是更底层的比如网络库，才会直接涉及适配不同版本系统的情况。
- 当你必须支持某个更新系统特性的时候，也必须选择更高版本的系统，比如 io_uring。
- 前面提到的使用 musl libc 的情况，如果你是静态链接 musl libc(这确实是 musl libc 的主要使用方式)，可能会导致有些开源库无法使用的情况，比如开源协议明确要求只能动态链接。甚至当你的应用需要基于动态库做插件机制时，也会带来一些负面影响。
- 很多国产 Linux 系统的内核版本和 glibc 版本已经比较高了，一般不存在升级困难的问题。

## 我现在的开发环境

虽然上文的方案已经能让我使用最新的工具链编译出能运行在更低的 Windows 和 Linux 系统上的程序了。但是，作为一名"优秀"的程序员，如果没有更高的追求，跟咸鱼有什么区别？

### 结构化并发

截至 2026 年 8 月，处于 AI 时代的我们，我想市面上大部分的软件应该都离不开操作磁盘 IO 和网络 IO 了吧？既然要处理 IO，就避免不了异步编程，有了异步，就不可避免地为代码引入生命周期管理的复杂度，也就不可避免地写出 BUG。因此，具有更高追求的程序员应该开始**面向结构化并发编程**。

但结构化并发意味着异步任务不能被强制结束，只要异步任务被启动，就必须等待其自己运行结束。那么，怎样才算自己运行结束，在我看来，需要满足以下情况之一：

1. 完整执行完成：执行成功。此时该异步任务及其所有子任务都运行结束，所有现场全部清理干净。
2. 抛出异常：执行失败。抛异常也是异步任务需要处理的退出路径，此时要么异步任务自己处理异常并处理好所有对象的生命周期，要么交给父任务处理（相当于父任务也抛了异常）。总之，异常发生后，所有现场也全部清理干净。
3. 被取消：取消。这是最重要的部分，一个等待系统通知的异步任务，不应该被强制停止，而是通过取消机制让其有机会打扫现场。但是，取消机制本身依赖操作系统内核。

也就是说，结构化并发要求所有异步任务都能有一个统一的入口和统一的出口；所有异步任务的生命周期都严格嵌套在特定的作用域下；也不会出现父任务停止了，子任务还在跑的情况。满足结构化并发的程序，其内部的逻辑结构将非常清晰，回调满天飞的情况将彻底终结，BUG 也将大大减少。当你对满足结构化并发的正在运行的程序执行 Ctrl-C 或发送终止信号时，程序不会强制终止，而是将队列中未运行的任务丢弃(任务没有执行，析构函数会自动清理资源)、为所有正在运行的任务发送取消信号、等待所有子线程退出，最终主线程最后退出，整个程序完美结束。

### 选择满足要求的最低版本系统

#### 选择 Windows 系统版本

让我们的异步 IO 程序真正做到结构化并发，同时也对操作系统版本提出了要求。正如前文所说，取消是需要操作系统内核支持的，而 Windows Vista 之前只有 [CancelIo](https://learn.microsoft.com/en-us/windows/win32/fileio/cancelio) 接口，该接口只有一个 HANDLE 参数，即无法区分当前 HANDLE 上投递的多个 IO 请求，并且调用 CancelIo 的线程必须是 IO 被提交的线程，因此，该接口满足不了真正的取消语义。而从 Vista 开始，Windows 内核引入了 [CancelIoEx](https://learn.microsoft.com/en-us/windows/win32/fileio/cancelioex-func) 才真正满足了要求。

[Asio](https://github.com/chriskohlhoff/asio) 源码中也在 `cancel()` 接口中明确说明了 CancelIo 的问题：

```c++
/// Cancel all asynchronous operations associated with the file.
  /**
   * This function causes all outstanding asynchronous read and write
   * operations to finish immediately, and the handlers for cancelled
   * operations will be passed the asio::error::operation_aborted error.
   *
   * @throws asio::system_error Thrown on failure.
   *
   * @note Calls to cancel() will always fail with
   * asio::error::operation_not_supported when run on Windows XP, Windows
   * Server 2003, and earlier versions of Windows, unless
   * ASIO_ENABLE_CANCELIO is defined. However, the CancelIo function has
   * two issues that should be considered before enabling its use:
   *
   * @li It will only cancel asynchronous operations that were initiated in the
   * current thread.
   *
   * @li It can appear to complete without error, but the request to cancel the
   * unfinished operations may be silently ignored by the operating system.
   * Whether it works or not seems to depend on the drivers that are installed.
   *
   * For portable cancellation, consider using the close() function to
   * simultaneously cancel the outstanding operations and close the file.
   *
   * When running on Windows Vista, Windows Server 2008, and later, the
   * CancelIoEx function is always used. This function does not have the
   * problems described above.
   */
#if defined(ASIO_MSVC) && (ASIO_MSVC >= 1400) \
  && (!defined(_WIN32_WINNT) || _WIN32_WINNT < 0x0600) \
  && !defined(ASIO_ENABLE_CANCELIO)
  __declspec(deprecated("By default, this function always fails with "
        "operation_not_supported when used on Windows XP, Windows Server 2003, "
        "or earlier. Consult documentation for details."))
#endif
  void cancel()
  {
    asio::error_code ec;
    impl_.get_service().cancel(impl_.get_implementation(), ec);
    asio::detail::throw_error(ec, "cancel");
  }
```

其实从 Vista 开始，Windows 内核引入了很多新特性，以至于完全可以将 Vista 定义为现代 Windows 内核的起点。只不过 Vista 发行后问题很多，后续 Windows 7 出现后，用户也都是直接从 XP 升级到了 Windows 7。目前市面上也已经没有 Vista 系统的存量了，桌面版最低从 XP 开始，直接跳过 Vista 到 Windows 7/8/10/11，服务器版最低从 Windows Server 2003 开始，其中 Windows Server 2008 对应的正是 Vista 版的内核，不过从 Windows Server 2008 R2 开始就和 Windows 7 对齐了。

因此，截至今天，对于必须支持 XP 的场景，我们可以以半结构化的方式去解决。但是，从面向未来的角度来讲，我强烈建议所有开发者将最低支持的 Windows 版本提高到 Windows 7。这也是我今天的选择。

#### 选择 Linux 系统版本

Linux 平台相比 Windows 在异步 IO 上做得更差些。Windows 的 IOCP 是很早就有的技术，而 Linux 的 io_uring 直到 5.1 版本才引入，也就是说，Linux 真正的异步 IO 机制落后了 Windows 几十年。

至于 libaio 这种纯纯的残次品，只支持文件 IO，而且必须要使用 DIRECT IO 才能达到异步的效果。更离谱的是，它的 `io_cancel` API 完全不可用，大部分文件系统的实现都是返回 EAGAIN 错误码。说句心里话，如果不是 io_uring 出得晚，还有那么多不支持 io_uring 的生产环境在运行着，我根本不想支持缺少 io_uring 的 Linux 系统。

好消息是 Linux 下同步文件 IO 性能并不差，只要在读写线程恰当地处理外部的取消请求，也能做到结构化并发。毕竟一次 IO 请求的完成时间一定是有界的，且大部分情况下都很快（卡死的情况就不算了，这种 kill -9 都杀不掉）。

不过，我遇到过 Linux 下使用同步 IO 读写分布式存储暴露的文件系统下的文件时性能非常差的情况，通过使用 libaio 解决，性能提升非常大。考虑到 libaio 最低支持到 Linux 2.6 内核，因此，在没有 io_uring 的情况下，我们依然可以使用同步 IO 或 libaio，把最低支持做到 RedHat 4。

尽管如此，我依然建议所有开发者将最低支持的 Linux 系统提高到 RedHat 7。一方面工具链是现成的；另一方面 RedHat 7 对应的内核和 glibc 版本完全能够应付几乎所有国产操作系统版本了。真要遇到必须支持的特别低的情况，按照前文说的方式也能解决。

同时，对于能够掌控运行环境的开发者，强烈建议将支持的最低 Linux 系统提高到 Linux 5.1+，以满足支持 io_uring 的要求。

额外说一点，Windows 和 Linux 的异步 IO 机制还是有很大的区别，而且设计上存在不一致的地方。部分内容可以参考我在 [记一次 Asio Windows 文件后端的偏移量 BUG](/blog/posts/记一次-Asio-Windows-文件后端的偏移量-BUG/) 中的总结，这里不再详述。

### 最终的选择

写了那么多，总算回归到本文的主题了，现在总结下我的开发环境。

#### 支持的最低系统版本

- Windows：Windows 7 起步
- Linux：RedHat 7 起步（内核 3.10+）；自己的运行环境选择支持 io_uring 的 5.1+ 内核。

部分理由见上文，另外还因为很多重要的 C++ 库都已经上调了最低支持的 Windows 版本，而且普遍都选择了 Windows 7。

#### 编译工具链

- Windows：选择 Mingw-w64 官方预编译的 x86_64-16.2.0-release-win32-seh-msvcrt-rt_v14-rev1.7z。官方的 VS 我会在真正需要的时候引入。
- Linux：直接使用最新发行版自带的工具链，需要考虑低版本系统时使用 Pixi 提供的 glibc 2.17 的 sysroot 和 GCC 16 工具链

理由见上文。

#### 构建系统

选择 XMake 作为跨平台的构建系统，理由如下：

- 基于 Lua：构建配置写起来非常舒服，CMake 的那套 DSL 又丑又难写。
- 更跨平台：CMake 的高版本无法运行在低版本的 Linux 系统上，但是 XMake 可以(使用自己的 tbox 对接底层 libc 和系统 API，类似 glib，注意 glib 不是 glibc)。
- 包管理：CMake 没有内置的包管理，引入第三方库比较麻烦（FetchContent 当然能做，用 git 子模块也行），我更喜欢 XMake 开箱即用的包管理能力，还支持自建私有仓库。

#### 编辑器/IDE

选择 VSCode 作为跨平台的编辑器，理由如下：

- 跨平台：Windows 和 Linux 都能完美运行。
- 远程开发：其 Remote SSH 插件完美支持远程开发需求，Linux 开发机可以不需要桌面环境。
- 插件丰富：通过各种插件可以将其打造出功能强大的 IDE。

我常用的 VSCode 插件：

- Remote SSH: 用于远程开发。
- C/C++: 用于调试，智能提示我会交给 clangd。
- CMake/XMake: 用于为构建系统的 DSL 提供语法高亮和智能提示。虽然我自己的新项目不再使用 CMake，但是考虑到三方库大量使用 CMake，因此我依然会安装 CMake 插件。
- CMake Tools: 用于编译 CMake 项目
- clangd: 用于智能提示、格式化、静态分析
- Git Graph: 提供管理 Git 仓库的功能。
- GitLens: 比 Git Graph 功能更强大，虽然核心功能收费，但是免费功能依然很有用，我一般搭配 Git Graph 使用。

```json
          "when": "editorTextFocus"
    },

    // 跳转到声明
    {
        "key": "alt+f2",
        "command": "editor.action.revealDeclaration"
    },

    // 跳转到定义
    {
        "key": "f2",
        "command": "editor.action.revealDefinition",
        "when": "editorHasDefinitionProvider && editorTextFocus && !isInEmbeddedEditor"
    }
]
```

## AI 时代的一些思考

这两年环境里变化最大的部分就是 AI。人人都在用 AI 写代码，包括我现在也严重依赖 AI 帮我写代码（但我会确保看懂所有核心代码）。昨天我还刷到一个 AI 短剧：若干年后，连一个会配置 DNS 的人都找不到了……不可否认，AI 确实极大地提高了我们的生产力。有了 AI，好像我们的能力也跟着变强了。但是，AI 也确确实实带来了严重的弊端：

- 失业率上升：老板觉得一个 AI 能完成之前好几个人才能完成的工作，于是裁员更多了。
- 效率提升不代表工作更轻松：我自己的体验和网友的反馈都表明大家似乎更累了，熬夜也更多了；公司分配给自己的活更多了，给的时间也更少了；
- 新人失去了学习和工作的机会：AI 成了那些应届毕业生最直接的竞争对手，一个 AI 就是一名专家。
- 迷失了方向：AI 让很多人觉得我一个人啥都能做了。于是，为了想办法赚钱，开始想各种各样的点子让 AI 去实现。可是成功者总归是少数，大部分人忙到最后可能什么也没得到。
- 失去控制的业务系统：这是我作为开发者最不能接受的地方。现在人人用 AI 写代码，做产品，到头来却一行代码都看不懂。做原型验证或者自己玩玩还可以理解。但真正要上线部署、真金白银卖给客户的时候，有没有认真考虑过后期的运维和升级？有没有认真考虑过数据安全？
- ...

AI 时代，拥抱 AI 是没问题的，但是我们一定要做 AI 的主人而不是做 AI 的奴隶。
