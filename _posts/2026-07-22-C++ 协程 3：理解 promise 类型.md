## 协程概念

协程 TS 增加了三个关键字：`co_await`、`co_yield` 和 `co_return`。函数体中只要出现其中一个，编译器就会把这个函数当作协程处理。

编译器会执行一系列相当机械的转换，把函数改写成状态机，使它能在特定位置挂起，之后再恢复。

上一篇介绍了协程 TS 两套新接口中的 **Awaitable**。另一套对代码转换同样重要的接口是 **Promise**。

**Promise** 接口用于定制协程本身。库作者可以决定协程被调用时发生什么，正常返回或因未处理异常退出时发生什么，还可以定制协程体内每个 `co_await` 和 `co_yield` 表达式。

## Promise 对象

**Promise** 对象实现了一组由编译器在协程执行到特定位置时调用的方法，借此定义并控制协程行为。

> 先放下对“promise”这个词的既有印象。在某些用法中，协程 Promise 对象的角色确实有点像与 `std::future` 配对的 `std::promise`；换到其他用法，这种类比就很勉强。更合适的理解是把它看成“协程状态控制器”：它控制协程行为，也可以记录协程状态。

每次调用协程函数，都会在协程帧中构造一个 Promise 对象。

编译器会在协程执行的关键位置生成代码，调用 Promise 对象的相应方法。

下文把某次协程调用所创建的 Promise 对象记作 `promise`。

假设函数体 `<body-statements>` 中出现了 `co_return`、`co_await` 或 `co_yield`，编译器会把协程体大致转换成下面这样：

```c++
{
  co_await promise.initial_suspend();
  try
  {
    <body-statements>
  }
  catch (...)
  {
    promise.unhandled_exception();
  }
FinalSuspend:
  co_await promise.final_suspend();
}
```

调用协程函数后，真正执行源码中的协程体之前还要完成一系列步骤，这一点与普通函数不同。

先列出流程，后面再逐项展开：

1. 用 `operator new` 分配协程帧，这次分配可能被优化掉；
2. 把函数参数复制到协程帧；
3. 构造类型为 `P` 的 Promise 对象；
4. 调用 `promise.get_return_object()`，取得协程首次挂起时返回给调用方的对象，并把它存入局部变量；
5. 调用 `promise.initial_suspend()`，再对结果执行 `co_await`；
6. `co_await promise.initial_suspend()` 恢复后，无论是立即恢复还是异步恢复，开始执行源码中的协程体。

执行到 `co_return` 时，还会完成以下步骤：
1. 调用 `promise.return_void()` 或 `promise.return_value(<expr>)`；
2. 按构造顺序的逆序销毁所有自动存储期变量；
3. 调用 `promise.final_suspend()`，再对结果执行 `co_await`。

如果未处理异常逃出 `<body-statements>`，流程则是：
1. 捕获异常，在 `catch` 块中调用 `promise.unhandled_exception()`；
2. 调用 `promise.final_suspend()`，再对结果执行 `co_await`。

执行离开协程体后，协程帧会被销毁：
1. 调用 Promise 对象的析构函数；
2. 调用各个参数副本的析构函数；
3. 调用 `operator delete` 释放协程帧占用的内存，这一步也可能被优化掉；
4. 把控制权交还给调用方或恢复方。

协程第一次执行到某个 `co_await` 中的 `<return-to-caller-or-resumer>` 时会挂起；如果此前已经运行结束，则协程帧会被销毁。无论是哪种情况，先前由 `promise.get_return_object()` 得到的返回对象都会交给协程调用方。

### 分配协程帧

编译器首先生成对 `operator new` 的调用，为协程帧分配内存。

如果 Promise 类型 `P` 定义了自己的 `operator new`，就调用这个重载；否则调用全局 `operator new`。

这里有几个细节。

传给 `operator new` 的大小不是 `sizeof(P)`，而是整个协程帧的大小。编译器根据参数、Promise 对象和局部变量的数量与大小，再加上管理协程状态所需的实现专用空间，自动计算这个值。

同时满足以下条件时，编译器可以优化掉这次 `operator new` 调用：
* 能确定协程帧的生命周期严格包含在调用方的生命周期内；
* 在调用点能够确定所需协程帧的大小。

此时，编译器可以直接从调用方的活动帧中分配协程帧空间，具体可能位于其栈帧或协程帧部分。

协程 TS 没有规定任何保证消除分配的场景，所以代码仍须按分配可能抛出 `std::bad_alloc` 来编写。通常不应把协程函数声明为 `noexcept`，除非你接受协程帧分配失败时调用 `std::terminate()`。

还有一条不用异常处理分配失败的备用路径。嵌入式系统等禁用异常的环境，或不能承受异常开销的高性能场景，可能需要它。

如果 Promise 类型提供静态成员函数 `P::get_return_object_on_allocation_failure()`，编译器就会调用 `operator new(size_t, nothrow_t)` 重载。分配返回 `nullptr` 时，协程不会抛异常，而是立即调用这个静态成员，并把结果返回给调用方。

#### 定制协程帧的内存分配

Promise 类型可以重载 `operator new()`，让使用该 Promise 的协程帧采用自定义分配逻辑，而不走全局 `operator new`。

例如：
```c++
struct my_promise_type
{
  void* operator new(std::size_t size)
  {
    void* ptr = my_custom_allocate(size);
    if (!ptr) throw std::bad_alloc{};
    return ptr;
  }

  void operator delete(void* ptr, std::size_t size)
  {
    my_custom_free(ptr, size);
  }

  ...
};
```

如果想使用调用方传入的自定义分配器，还需要再走一步。

`P::operator new()` 还可以接收额外参数。只要能找到匹配的重载，编译器就会把协程函数各参数的左值引用传给它。这样，`operator new` 就能调用作为协程参数传入的分配器的 `allocate()` 方法。

不过还得在分配出的内存里保存一份分配器副本，供对应的 `operator delete` 使用。协程参数不会传给 `operator delete`，因为它们存放在协程帧中，到调用 `operator delete` 时已经销毁。

一种做法是在协程帧末尾多分配一段空间，用来保存分配器副本，释放协程帧时再取出来。

例如：
```c++
template<typename ALLOCATOR>
struct my_promise_type
{
  template<typename... ARGS>
  void* operator new(std::size_t sz, std::allocator_arg_t, ALLOCATOR& allocator, ARGS&... args)
  {
    // Round up sz to next multiple of ALLOCATOR alignment
    std::size_t allocatorOffset =
      (sz + alignof(ALLOCATOR) - 1u) & ~(alignof(ALLOCATOR) - 1u);

    // Call onto allocator to allocate space for coroutine frame.
    void* ptr = allocator.allocate(allocatorOffset + sizeof(ALLOCATOR));

    // Take a copy of the allocator (assuming noexcept copy constructor here)
    new (((char*)ptr) + allocatorOffset) ALLOCATOR(allocator);

    return ptr;
  }

  void operator delete(void* ptr, std::size_t sz)
  {
    std::size_t allocatorOffset =
      (sz + alignof(ALLOCATOR) - 1u) & ~(alignof(ALLOCATOR) - 1u);

    ALLOCATOR& allocator = *reinterpret_cast<ALLOCATOR*>(
      ((char*)ptr) + allocatorOffset);

    // Move allocator to local variable first so it isn't freeing its
    // own memory from underneath itself.
    // Assuming allocator move-constructor is noexcept here.
    ALLOCATOR allocatorCopy = std::move(allocator);

    // But don't forget to destruct allocator object in coroutine frame
    allocator.~ALLOCATOR();

    // Finally, free the memory using the allocator.
    allocatorCopy.deallocate(ptr, allocatorOffset + sizeof(ALLOCATOR));
  }
}
```

要让第一个参数为 `std::allocator_arg` 的协程使用这个 `my_promise_type`，需要特化 `coroutine_traits`。后文还会详细介绍这个类。

例如：
```
namespace std::experimental
{
  template<typename ALLOCATOR, typename... ARGS>
  struct coroutine_traits<my_return_type, std::allocator_arg_t, ALLOCATOR, ARGS...>
  {
    using promise_type = my_promise_type<ALLOCATOR>;
  };
}
```

即便定制了内存分配策略，**编译器仍然可以优化掉分配器调用**。

### 把参数复制到协程帧

协程必须把调用方传入的参数复制到协程帧，使它们在协程挂起后仍然有效。

按值传递的参数通过移动构造函数转移到协程帧。

按左值引用或右值引用传递时，复制到协程帧的只有引用，不包括引用指向的对象。

如果参数类型可平凡析构，并且协程在任何可达的 `<return-to-caller-or-resumer>` 之后都不再引用它，编译器可以省略这个参数副本。

把参数按引用传入协程很容易出问题，因为被引用对象未必能活过整个协程。完美转发、转发引用等在普通函数中常见的技巧，直接用于协程可能导致未定义行为。Toby Allsopp 的[这篇文章](https://toby-allsopp.github.io/2017/04/22/coroutines-reference-params.html)对此有更详细的讨论。

如果参数的复制或移动构造函数抛出异常，已经构造的参数会被销毁，协程帧会被释放，异常则传播给调用方。

### 构造 Promise 对象

所有参数进入协程帧后，协程开始构造 Promise 对象。

参数要先于 Promise 对象复制，是为了让 Promise 构造函数能够访问复制后的参数。

编译器先查找能接收所有参数副本之左值引用的 Promise 构造函数重载。找到就调用该重载；找不到则调用 Promise 类型的默认构造函数。

让 Promise 构造函数“查看”参数，是协程 TS 当时一项较新的修改。它在 2018 年 Jacksonville 会议上随 [N4723](http://wg21.link/N4723) 获得采纳，提案见 [P0914R1](http://wg21.link/P0914R1)。因此，一些较老的 Clang 或 MSVC 版本可能尚不支持。

如果 Promise 构造函数抛出异常，栈展开过程会先销毁参数副本并释放协程帧，再把异常传播给调用方。

### 获取返回对象

协程对 Promise 对象做的第一件事，是调用 `promise.get_return_object()` 取得返回对象（return object）。

协程首次挂起时，或者在首次挂起前就运行结束时，这个返回对象会交给协程调用方。

非常粗略地看，控制流如下：
```c++
// Pretend there's a compiler-generated structure called 'coroutine_frame'
// that holds all of the state needed for the coroutine. Its constructor
// takes a copy of parameters and default-constructs a promise object.
struct coroutine_frame { ... };

T some_coroutine(P param)
{
  auto* f = new coroutine_frame(std::forward<P>(param));

  auto returnObject = f->promise.get_return_object();

  // Start execution of the coroutine body by resuming it.
  // This call will return when the coroutine gets to the first
  // suspend-point or when the coroutine runs to completion.
  coroutine_handle<decltype(f->promise)>::from_promise(f->promise).resume();

  // Then the return object is returned to the caller.
  return returnObject;
}
```

返回对象必须在启动协程体之前取得。协程帧及其 Promise 对象可能在 `coroutine_handle::resume()` 返回前就被销毁，销毁动作甚至可能发生在另一个线程；等协程体开始执行后再调用 `get_return_object()` 并不安全。

### 初始挂起点

协程帧初始化完成、返回对象也已取得后，下一步执行 `co_await promise.initial_suspend();`。

`promise_type` 的作者可以借此决定：协程是在进入源码中的协程体之前先挂起，还是立即开始执行协程体。

如果协程在初始挂起点挂起，之后可以在合适的时机对其 `coroutine_handle` 调用 `resume()` 或 `destroy()`，恢复或销毁协程。

`co_await promise.initial_suspend()` 的结果会被丢弃，因此 Awaiter 的 `await_resume()` 通常返回 `void`。

这条语句位于保护其余协程体的 `try`/`catch` 之外。对 `co_await promise.initial_suspend()` 求值时，如果在到达 `<return-to-caller-or-resumer>` 前抛出异常，协程帧和返回对象会先被销毁，异常再抛给协程调用方。

如果返回对象采用 RAII 语义、析构时会销毁协程帧，这里尤其要小心。此时必须保证 `co_await promise.initial_suspend()` 为 `noexcept`，避免协程帧被重复释放。

> 当时有人建议调整语义，把 `co_await promise.initial_suspend()` 的全部或一部分放进协程体的 `try`/`catch`。因此，在协程规范最终定稿前，这里的确切语义仍可能改变。

许多协程的 `initial_suspend()` 只返回两种类型之一：惰性启动时返回 `std::experimental::suspend_always`，立即启动时返回 `std::experimental::suspend_never`。两者都是 `noexcept` 的 Awaitable，因此通常不会触发上述问题。

### 把返回对象交给调用方

协程到达第一个 `<return-to-caller-or-resumer>` 时，`get_return_object()` 产生的返回对象会交给调用方。如果协程没到达这里就已经运行结束，同样会交还这个对象。

返回对象的类型不必与协程函数声明的返回类型相同，必要时会执行隐式转换。

> Clang 5.0 的协程实现会把转换推迟到返回对象真正离开协程调用时；MSVC 2017 Update 3 则在调用 `get_return_object()` 后立即转换。协程 TS 当时没有明确规定应该采用哪种行为。据我了解，MSVC 计划改成更接近 Clang 的方式，因为延迟转换可以支持一些[有趣的用例](https://github.com/toby-allsopp/coroutine_monad)。

### 使用 `co_return` 从协程返回

协程执行到 `co_return` 时，编译器会把它转换为对 `promise.return_void()` 或 `promise.return_value(<expr>)` 的调用，随后执行 `goto FinalSuspend;`。

转换规则如下：
* `co_return;`  
  -> `promise.return_void();`
* `co_return <expr>;`  
  -> `<expr>; promise.return_void();`，当 `<expr>` 的类型为 `void`；  
  -> `promise.return_value(<expr>);`，当 `<expr>` 的类型不是 `void`。

随后的 `goto FinalSuspend;` 会在求值 `co_await promise.final_suspend();` 之前，按构造顺序的逆序销毁所有自动存储期局部变量。

如果协程没有 `co_return`，执行直接越过函数体末尾，效果等同于末尾有一条 `co_return;`。此时若 `promise_type` 没有 `return_void()` 方法，则行为未定义。

如果求值 `<expr>`，或者调用 `promise.return_void()`、`promise.return_value()` 时抛出异常，异常仍会进入 `promise.unhandled_exception()`，后文会讲到。

### 处理从协程主体传播出来的异常

异常逃出协程体后会被捕获，并在 `catch` 块中调用 `promise.unhandled_exception()`。

这个方法通常调用 `std::current_exception()` 捕获当前异常，并保存下来，以便稍后在另一个上下文中重新抛出。

另一种实现是在方法中执行 `throw;`，立即重抛异常，例如 [folly::Optional](https://github.com/facebook/folly/blob/4af3040b4c2192818a413bad35f7a6cc5846ed0b/folly/Optional.h#L587)。这样做很可能会立即销毁协程帧，并把异常传播给调用方或恢复方。某些抽象假定或要求 `coroutine_handle::resume()` 为 `noexcept`，重抛会破坏这个假设。因此，只有在完全控制谁会调用 `resume()` 时，才适合采用这种方式。

如果 `unhandled_exception()` 重抛异常，或者 `try` 块之外的逻辑抛出异常，当时的[协程 TS](http://wg21.link/N4736) 对预期行为的措辞[并不清楚](https://github.com/GorNishanov/CoroutineWording/issues/17)。

我当时的理解是，只要控制流离开协程体，协程帧就会在控制权回到调用方或恢复方之前自动销毁。这既包括异常从 `co_await promise.initial_suspend()`、`promise.unhandled_exception()` 或 `co_await promise.final_suspend()` 传播出去，也包括 `co_await p.final_suspend()` 同步完成、协程直接运行结束的情况。不过，这种解释本身也有问题。

后续版本的协程规范应该会澄清这一点。在此之前，我会保证 `initial_suspend()`、`final_suspend()` 和 `unhandled_exception()` 都不抛异常。

### 最终挂起点

执行离开用户编写的协程体后，结果已经由 `return_void()`、`return_value()` 或 `unhandled_exception()` 接收，局部变量也已销毁。此时，协程在把控制权交还给调用方或恢复方之前，还能执行一段附加逻辑。

这段逻辑从 `co_await promise.final_suspend();` 开始。

协程可以在这里发布结果、发出完成信号，或者恢复某个后续协程。它也可以在运行结束前挂起，让外部随后销毁协程帧。

对挂起在 `final_suspend` 的协程调用 `resume()` 是未定义行为。协程一旦挂在这里，外部只能 `destroy()` 它。

Gor Nishanov 解释说，这项限制能减少协程需要表示的挂起状态，也可能减少分支数量，从而给编译器更多优化空间。

协程可以选择不在 `final_suspend` 挂起，不过**最好尽量让协程挂在 `final_suspend`**。这样就必须从协程外部调用 `.destroy()`，通常由某个 RAII 对象的析构函数完成。明确的外部销毁点有助于编译器判断协程帧生命周期是否包含在调用方内部，进而更有机会消除协程帧的内存分配。

### 编译器如何选择 Promise 类型

下面看编译器如何确定某个协程使用哪种 Promise 类型。

Promise 对象的类型由 `std::experimental::coroutine_traits` 根据协程签名推导。

假设协程函数的签名是：
```c++
task<float> foo(std::string x, bool flag);
```

编译器把返回类型和参数类型传给 `coroutine_traits`，由此取得 Promise 类型：
```c++
typename coroutine_traits<task<float>, std::string, bool>::promise_type;
```

如果协程是非静态成员函数，类类型会作为第二个模板参数传入 `coroutine_traits`。成员函数带右值引用限定符时，这个模板参数也是右值引用。

例如，考虑以下两个成员函数：
```c++
task<void> my_class::method1(int x) const;
task<foo> my_class::method2() &&;
```

编译器会使用以下 Promise 类型：
```c++
// method1 promise type
typename coroutine_traits<task<void>, const my_class&, int>::promise_type;

// method2 promise type
typename coroutine_traits<task<foo>, my_class&&>::promise_type;
```

`coroutine_traits` 的默认实现查找返回类型中嵌套的 `promise_type` 类型别名。实际定义还带有一些 SFINAE 处理，使 `RET::promise_type` 不存在时，`coroutine_traits` 也不定义 `promise_type`。
```c++
namespace std::experimental
{
  template<typename RET, typename... ARGS>
  struct coroutine_traits<RET, ARGS...>
  {
    using promise_type = typename RET::promise_type;
  };
}
```

如果协程返回类型由你控制，只要在类中定义嵌套的 `promise_type`，编译器就会把它用作该类所对应协程的 Promise 类型。

例如：
```c++
template<typename T>
struct task
{
  using promise_type = task_promise<T>;
  ...
};
```

如果无法修改返回类型，可以特化 `coroutine_traits` 来指定 Promise 类型。

例如，可以为返回 `std::optional<T>` 的协程指定 Promise 类型：
```c++
namespace std::experimental
{
  template<typename T, typename... ARGS>
  struct coroutine_traits<std::optional<T>, ARGS...>
  {
    using promise_type = optional_promise<T>;
  };
}
```

### 标识某个协程帧

调用协程函数会创建一个协程帧。之后要恢复对应协程或销毁这个帧，就需要一种方式来引用它。

协程 TS 为此提供了 `coroutine_handle` 类型。

它的简化接口如下：
```c++
namespace std::experimental
{
  template<typename Promise = void>
  struct coroutine_handle;

  // Type-erased coroutine handle. Can refer to any kind of coroutine.
  // Doesn't allow access to the promise object.
  template<>
  struct coroutine_handle<void>
  {
    // Constructs to the null handle.
    constexpr coroutine_handle();

    // Convert to/from a void* for passing into C-style interop functions.
    constexpr void* address() const noexcept;
    static constexpr coroutine_handle from_address(void* addr);

    // Query if the handle is non-null.
    constexpr explicit operator bool() const noexcept;

    // Query if the coroutine is suspended at the final_suspend point.
    // Undefined behaviour if coroutine is not currently suspended.
    bool done() const;

    // Resume/Destroy the suspended coroutine
    void resume();
    void destroy();
  };

  // Coroutine handle for coroutines with a known promise type.
  // Template argument must exactly match coroutine's promise type.
  template<typename Promise>
  struct coroutine_handle : coroutine_handle<>
  {
    using coroutine_handle<>::coroutine_handle;

    static constexpr coroutine_handle from_address(void* addr);

    // Access to the coroutine's promise object.
    Promise& promise() const;

    // You can reconstruct the coroutine handle from the promise object.
    static coroutine_handle from_promise(Promise& promise);
  };
}
```

取得协程 `coroutine_handle` 有两种方式：
1. 它在 `co_await` 表达式期间传递给 `await_suspend()` 方法。
2. 如果持有协程 Promise 对象的引用，可以用 `coroutine_handle<Promise>::from_promise()` 重建对应的 `coroutine_handle`。

协程在 `co_await` 的 `<suspend-point>` 挂起后，它的 `coroutine_handle` 会传给 Awaiter 的 `await_suspend()`。可以把这个句柄理解为[续体传递风格](https://en.wikipedia.org/wiki/Continuation-passing_style)调用中的协程续体。

`coroutine_handle` **不是 RAII 对象**。必须手动调用 `.destroy()` 才会销毁协程帧并释放资源，可以把它类比为管理内存时使用的 `void*`。这样设计是出于性能考虑；如果句柄本身拥有资源，可能需要引用计数等机制，给协程增加额外开销。

实际使用时，最好选择为协程提供 RAII 语义的高层类型，例如 [cppcoro](https://github.com/lewissbaker/cppcoro) 中的类型；也可以自己封装，在协程类型中管理协程帧的生命周期。

### 自定义 `co_await` 的行为

Promise 类型可以定制协程体内每个 `co_await` 表达式。

只要 Promise 类型定义了 `await_transform()`，编译器就会把协程体内每个 `co_await <expr>` 改写为 `co_await promise.await_transform(<expr>)`。

这项机制有几种重要用途。

**让原本不可等待的类型支持 `co_await`。**

例如，返回 `std::optional<T>` 的协程可以在 Promise 类型中提供一个接收 `std::optional<U>` 的 `await_transform()` 重载。它返回一个 Awaitable：optional 有值时产生 `U`，值为 `nullopt` 时挂起协程。

```c++
template<typename T>
class optional_promise
{
  ...

  template<typename U>
  auto await_transform(std::optional<U>& value)
  {
    class awaiter
    {
      std::optional<U>& value;
    public:
      explicit awaiter(std::optional<U>& x) noexcept : value(x) {}
      bool await_ready() noexcept { return value.has_value(); }
      void await_suspend(std::experimental::coroutine_handle<>) noexcept {}
      U& await_resume() noexcept { return *value; }
    };
    return awaiter{ value };
  }
};
```

**把 `await_transform` 重载声明为删除，可以禁止等待某些类型。**

例如，`std::generator<T>` 的 Promise 类型可以声明一个接收任意类型、但已删除的 `await_transform()` 成员函数模板。这样就基本禁用了协程体内的 `co_await`。

```c++
template<typename T>
class generator_promise
{
  ...

  // Disable any use of co_await within this type of coroutine.
  template<typename U>
  std::experimental::suspend_never await_transform(U&&) = delete;

};
```

**调整和改变通常可等待的值的行为**

例如，可以把 Awaitable 包装在 `resume_on()` 中，定义一种保证每次 `co_await` 都在指定执行器上恢复的协程类型，参见 `cppcoro::resume_on()`。

```c++
template<typename T, typename Executor>
class executor_task_promise
{
  Executor executor;

public:

  template<typename Awaitable>
  auto await_transform(Awaitable&& awaitable)
  {
    using cppcoro::resume_on;
    return resume_on(this->executor, std::forward<Awaitable>(awaitable));
  }
};
```

最后要注意，只要 Promise 类型定义了*任意一个* `await_transform()` 成员，编译器就会让*所有* `co_await` 表达式调用 `promise.await_transform()`。如果只想定制部分类型，还需要提供一个原样转发参数的后备重载。

### 自定义 `co_yield` 的行为

Promise 类型还能定制 `co_yield` 的行为。

协程中的 `co_yield <expr>` 会被转换为 `co_await promise.yield_value(<expr>)`。Promise 类型因此可以定义一个或多个 `yield_value()` 方法，控制 `co_yield`。

`co_yield` 和 `await_transform` 有一点不同：Promise 类型如果没有定义 `yield_value()`，`co_yield` 就没有默认行为。换句话说，Promise 类型需要用删除的 `await_transform()` 显式禁用 `co_await`，却需要通过定义 `yield_value()` 显式启用 `co_yield`。

带 `yield_value()` 的典型 Promise 类型来自 `generator<T>`：
```c++
template<typename T>
class generator_promise
{
  T* valuePtr;
public:
  ...

  std::experimental::suspend_always yield_value(T& value) noexcept
  {
    // Stash the address of the yielded value and then return an awaitable
    // that will cause the coroutine to suspend at the co_yield expression.
    // Execution will then return from the call to coroutine_handle<>::resume()
    // inside either generator<T>::begin() or generator<T>::iterator::operator++().
    valuePtr = std::addressof(value);
    return {};
  }
};
```
