磁带库很多人可能不知道，但是磁带大部分人一定玩过。作为 90 后，我当年上初中时用小霸王听英语听力和音乐，它们都是以磁带为载体，只是随着时代的发展，磁带在日常生活中几乎已经看不到了。

那么，什么是磁带库呢？简单来讲，就是一系列磁带的集合，一般一台磁带库能存放几十甚至上百合磁带。和小时候玩的磁带不同，磁带库中的磁带容量更大，需要专用的硬件进行集中管理，而且价格昂贵，哪怕是入门级的磁带库都需要数万块才能买得到。

正是因为磁带库特别昂贵，本文将站在开发者的角度演示如果使用 [mhvtl](https://github.com/markh794/mhvtl)（mh Virtual Tape Library）来完整搭建一个虚拟磁带库，并完整跑一遍“装带 → 备份 → 定位 → 恢复 → 校验”等流程。

## 先认识磁带库

动手之前还是需要先把“磁带库”这个东西讲清楚，只有这样，才能理解 mhvtl 是如何模拟它的。

### 为什么要有磁带库

大部分普通人可能对磁带的理解还停留在小时候用来听英语听力和音乐的阶段，甚至觉得磁带已经过时了。其实磁带一直是冷数据归档的主力：单盘 LTO-9 原生容量 18 TB，单位容量成本远低于硬盘；磁带拔出驱动器就是彻底离线的介质，天然“气隙”隔离，勒索软件根本拿它没办法；还能做成 WORM（一次写入、多次读取）满足合规要求。代价是只能顺序访问，适合大块流式的备份归档，不适合随机读写的在线业务。

但磁带真正的痛点在规模上：一台磁带机一次只装一盘，几百 TB 数据摊到成百上千盘磁带上，靠人手换带既慢又没法全天候值守。而磁带库则解决了这个问题：它把几十上百盘磁带装进一排排槽位，用机械臂按调度自动上下带，主机发出一条命令就能把任意一盘磁带挂在驱动器上进行读写。多驱动器的磁带库还能并行读写磁带，使性能最大化。

### 磁带库的组成

- **磁带机（drive）**：也叫驱动器，真正读写磁带的设备，一次只装一盘。
- **卡带（cartridge）**：介质本身，贴着条码标签供识别，条码里通常编码了介质类型。上文说的磁带，在磁带库中就是卡带，下文统一为磁带。
- **槽位（slot）**：一排排存放磁带的仓位，不工作的带子都待在槽里。
- **机械臂（robot / picker）**：在槽位和磁带机之间搬运磁带的机械手。有没有它，正是“磁带库”区别于“单台磁带机”的关键。可以认为，机械臂就代表一个磁带库。
- **导入/导出口（MAP，也叫 mailslot）**：不开机箱门就能往库里放带、取带的口子。

### 如何控制磁带库

一套磁带库对主机会暴露成**两类独立的 SCSI 设备**：

- **换带机（Medium Changer）**：负责指挥机械臂搬带，响应 `MOVE MEDIUM`、`READ ELEMENT STATUS` 这类命令。Linux 下由 `ch` 驱动接管，设备节点是 `/dev/sch*`，用户态可用 `mtx` 工具操作。下文统称为机械臂。
- **磁带机（Sequential-Access Device）**：负责读写数据和定位。Linux 下由 `st` 驱动接管，设备节点是 `/dev/st*`、`/dev/nst*`，用户态可用 `mt` 工具操作、`tar`/`dd` 工具可直接从设备节点读写数据。下文统称为驱动器。

所以一次完整的备份，是这两类设备的配合：先用 `mtx` 让机械臂把某个槽里的磁带装进某台驱动器，再对那台驱动器的设备节点用 `tar` 工具写数据。“先换带、再读写”这条分工，后面每一步操作都会反复出现。

### 数据如何布局

不同于硬盘上的文件系统，其文件可以随机分布，并且可以直接通过文件路径定位文件。而一盘带子上的多个“文件”其实是首尾相接、线性排布的，彼此用一个叫 **filemark（文件标记）** 的特殊标记分隔，带子末尾还有个 **EOD（数据结束标记）**。想读第三个文件，没法直接寻址，得让磁头从当前位置**向前跨过两个 filemark**才行，这正是后面 `mt fsf` 命令要干的事。

## 如何模拟磁带库

软件模拟一台真实的硬件设备，一定是要遵守该硬件设计的规范的。上文介绍了真实磁带库的相关概念，有了这些概念，mhvtl 就能顺理成章的将其模拟出来：

- **内核模块 `mhvtl.ko`**：真磁带库一般是通过 SAS/FC 卡挂到主机上的，而 mhvtl 则实现了一个内核驱动，该驱动注册成一个伪 SCSI HBA（主机总线适配器）。通过凭空造出的一条 SCSI 总线，mhvtl 便能让其虚拟出的设备像真设备一样通过该总线被内核的 `st`（磁带）和 `ch`（换带机）驱动发现并接管。
- **用户态守护进程**：`vtltape` 每个实例模拟一台驱动器，`vtllibrary` 每个实例模拟一个机械臂。它们接收内核转发来的 SCSI 命令（INQUIRY、READ ELEMENT STATUS、READ/WRITE……），按 SCSI 规范应答，并把“写到磁带上的数据”落进 `/opt/mhvtl` 下的文件中。

当需要换带时，执行路径为：`mtx` → `ch` 驱动 → `mhvtl.ko` → `vtllibrary` -> 维护进程内部状态
当需要备份/归档时，执行路径为：`tar` → `st` 驱动 → `mhvtl.ko` → `vtltape` → 磁盘文件。

## 安装依赖

由于 mhvtl 在 Rocky 9 没有现成的安装包，本文选择从源码编译，再加上后续测试，因此需要安装一系列的工具：

```bash
[root@dev-rl-tape ~]# dnf install -y git make gcc zlib-devel kernel-headers tar mtx mt-st sg3_utils lsscsi policycoreutils-python-utils
```

其中：

- git: 用于从 github 上拉源码
- make/gcc/zlib-devel/kernel-headers: 用于编译 mhvtl 用户态程序和内核驱动
- kernel-headers: 用于编译内核模块
- tar: 用于备份/归档数据
- mtx: 用于控制机械臂，提供 mtx 命令
- mt-st: 用于控制驱动器，提供 mt 命令
- lsscsi: 用于查看 SCSI 设备信息
- sg3_utils: 用于向 SCSI 设备发送 SCSI 命令
- policycoreutils-python-utils: 提供 semanage 命令，用于在安装时设置 selinux 上下文

需要注意的事，编译并运行内核驱动时必须确保编译时使用的内核头文件版本与运行时加载该驱动的内核版本一致。否则可能会导致驱动加载失败或运行时异常。

由于当前运行的系统内核版本已经落后于官方提供的内核头文件版本了，因此上述命令执行完，需要先升级内核：

```bash
# 当前运行的内核版本
[root@dev-rl-tape ~]# uname -r
5.14.0-570.17.1.el9_6.x86_64

# 已安装内核头文件的版本
[root@dev-rl-tape ~]# rpm -q kernel kernel-headers
kernel-5.14.0-570.17.1.el9_6.x86_64
kernel-headers-5.14.0-687.17.1.el9_8.x86_64

# 先升级内核
[root@dev-rl-tape ~]# dnf install -y kernel kernel-devel
[root@dev-rl-tape ~]# reboot

# 升级后的内核版本
[root@dev-rl-tape ~]# uname -r
5.14.0-687.17.1.el9_8.x86_64
```

## 编译并安装 mhvtl

第一次安装时可以参考源码目录下的 INSTALL 文件：

```bash
# 源码下载到指定位置
[root@dev-rl-tape ~]# cd /usr/src
[root@dev-rl-tape src]# git clone https://github.com/markh794/mhvtl.git
[root@dev-rl-tape src]# cd mhvtl

# 编译用户态程序
[root@dev-rl-tape mhvtl]# make -j

# 编译内核模块
[root@dev-rl-tape mhvtl]# cd kernel
[root@dev-rl-tape kernel]# make -j

# 确保内核模块的 vermagic 与运行内核一致
[root@dev-rl-tape kernel]# modinfo -F vermagic mhvtl.ko
5.14.0-687.17.1.el9_8.x86_64 SMP preempt mod_unload modversions

[root@dev-rl-tape mhvtl]# make install
```

## 配置虚拟磁带库

### 修改配置文件

mhvtl 编译安装完成后除了会生成上文中提到的主要工具和内核模块外，默认还会在 `/etc/mhvtl` 目录下生成需要的配置文件：

```bash
[root@dev-rl-tape mhvtl]# ll /etc/mhvtl/
total 28
-rw-r--r--. 1 root root 3600 Jul  6 07:32 device.conf
-rw-r--r--. 1 root root 3600 Jul  6 07:21 device.conf.orig
-rw-r--r--. 1 root root 1673 Jul  6 07:32 library_contents.10
-rw-r--r--. 1 root root 1673 Jul  6 07:21 library_contents.10.orig
-rw-r--r--. 1 root root 1753 Jul  6 07:32 library_contents.30
-rw-r--r--. 1 root root 1753 Jul  6 07:21 library_contents.30.orig
-rw-r--r--. 1 root root  295 Jul  6 07:21 mhvtl.conf
```

其中：

- device.conf： 用于定义磁带库的机械臂和驱动器的信息。允许同时定义多台磁带库。
- library_contents.*： 用于描述磁带库里有几台驱动器、几个槽位、每个槽里放了哪写磁带（靠条码标识）。后缀数字对应 device.conf 中的 Library ID。
- mhvtl.conf：用于定义 mhvtl 的全局配置，比如磁带文件的位置、磁带的容量以及其他配置。该配置由守护进程读取。

有了这些默认配置，我们可以在几乎不做任何修改的情况下，直接拥有两台可供使用的虚拟磁带库。为了方便，本文不再修改默认配置。

这里简单介绍下两个重要配置文件的格式。先看 `device.conf`：

```bash
[root@dev-rl-tape mhvtl]# cat /etc/mhvtl/device.conf

 Vendor identification: STK

 NAA: 10:22:33:44:ab:00:00:00

 Backoff: 400
# fifo: /var/tmp/mhvtl

 NAA: 10:22:33:44:ab:00:01:00

```

理论上，磁带库的机械臂和驱动器是物理上分离的设备，也就是说，二者之间在物理属性上没有任何关联关系。一个驱动器可以被拔出并插到其他磁带库上，如果驱动器损坏，也可以买新的驱动器换上去。因此，为了让某个驱动器关联到磁带库上，需要通过在驱动器的配置下指定 `Library ID` 。

再看磁带库 10 对应的 `library_contents.10` 文件：

```bash
[root@dev-rl-tape mhvtl]# cat /etc/mhvtl/library_contents.10
VERSION: 2

Drive 1:
Drive 2:
Drive 3:
Drive 4:

Picker 1:

MAP 1:
MAP 2:
MAP 3:
MAP 4:

Slot 1: E01001L8
Slot 2: E01002L8
...
Slot 22: CLN101L8
Slot 23: CLN102L6
Slot 24:
Slot 25:
Slot 38: F01038L6
Slot 39: F01039L6
```

可以看到，该磁带库有 1 个机械臂、4 个驱动器、4 个邮槽、39 个槽位，其中部分槽位没有插入任何磁带。

其中插入的磁带信息通过条码标识。这里需要注意的是：类似驱动器可以单独插拔替换，磁带也一样。真实的磁带库可以通过邮槽来移除或添加新的磁带。因此，为了能方便识别磁带是否受磁带库和驱动器支持，一般会在磁带的条码中将磁带支持的 LTO 标准等信息编码进去。如 `L8` 后缀表示该磁带支持到 `LTO-8` 标准、`CLN` 前缀表示该磁带是清洁带。

### 生成介质文件

上述配置只是“账本”，其中 `device.conf` 配置会在守护进程启动时自动创建代表机械臂和驱动器的进程。为了让机械臂和驱动器能有磁带可供操作，还需要根据 `library_contents.*` 配置文件来生成真正可供读写的空白磁带。由于 mhvtl 只是模拟磁带库，因此实际生成磁带是通过文件系统上的文件来表示的，写磁带就相当于写特定的文件。

为了让  真正的空白磁带还得生成。`make_vtl_media` 会读 `device.conf` + `library_contents.*`，为每个条码建一套后备文件：

现在，我们来创建真正的磁带：

```bash
[root@dev-rl-tape mhvtl]# make_vtl_media -C /etc/mhvtl -H /opt/mhvtl -c -f
===> Reading from /etc/mhvtl/device.conf file to find Tape Libraries and Drives ...
===> Scanning for 'Slot' entries in /etc/mhvtl/library_contents.10 ...
===> Creating entry: /opt/mhvtl/CLN101L8 ...
Creating tape data ...
Creating new media directory: /opt/mhvtl/CLN101L8
Creating new media mam files: /opt/mhvtl/CLN101L8/mam and /opt/mhvtl/CLN101L8/mhvtl_data
Creating new media data file: /opt/mhvtl/CLN101L8/data.0
Creating new media indx file: /opt/mhvtl/CLN101L8/indx.0

mktape: create_partition(): /opt/mhvtl/CLN101L8 files created
===> Creating entry: /opt/mhvtl/CLN102L6 ...
...
```

其中 `/opt/mhvtl` 为磁带的家目录，也就是磁带文件所在的目录，该目录在 `mhvtl.conf` 中配置，默认值为 `/opt/mhvtl`。因此，创建磁带时确保磁带的家目录和 `mhvtl.conf` 中配置一致，否则，相关进程启动后机械臂和驱动器可能找不到对应的磁带。

可以看到每盘磁带对应一个目录，磁带中未来将要存储的数据就在对应的目录中。其中目录中的文件：

- `data.0`：数据文件，用于实际存储写入磁带的数据
- `indx.0`：索引文件，包含一系列指向 data.0 文件的指针结构，用于快速定位数据在磁带上的物理位置
- `mam`：SCSI 磁带标准中定义的“介质辅助内存”，用于存储一些额外的、标准化的元数据信息
- `meta.0`：元数据文件，用于存储持久化的磁带元数据信息
- `mhvtl_data`：mhvtl 内部数据文件

## 启动虚拟磁带库

上述步骤做完，完整的磁带库基本就绪。但是由于相关守护进程尚未运行，因此，虚拟磁带库目前是不可见的。为了能真正使用虚拟磁带库，需要启动相关守护进程。

启动前先看下当前系统上的 SCSI 设备和驱动信息：


细心的读者可能注意到了，`nst` 设备名存在 `a`、`l`、`m` 等后缀，这些不同后缀的设备对应磁带不同的配置模式，用于不同的读写场景，本文就不再赘述，下文操作统一使用 `dev/nst0` 这类不带后缀的设备。

## 读写测试

下面我们执行完整“装带 → 备份 → 定位 → 恢复 → 校验”流程。下文以磁带库 10 为测试磁带库。

### 装带

第一步，需要先将其中一个空闲的磁带装入驱动器的槽位，这样才能对这盘磁带进行读写，这里选择将槽 1 的磁带（E01001L8）装进 0 号驱动器：

```bash
[root@dev-rl-tape mhvtl]# mtx -f /dev/sch0 load 1 0
Loading media from Storage Element 1 into drive 0...don

[root@dev-rl-tape mhvtl]# mtx -f /dev/sch0 status
  Storage Changer /dev/sch0:4 Drives, 43 Slots ( 4 Import/Export )
Data Transfer Element 0:Full (Storage Element 1 Loaded):VolumeTag = E01001L8
Data Transfer Element 1:Empty
Data Transfer Element 2:Empty
Data Transfer Element 3:Empty
      Storage Element 1:Empty
      Storage Element 2:Full :VolumeTag=E01002L8
...
```

可以看到 0 号驱动器变成 Full、槽 1 变空，磁带确实从槽位移进了驱动器。接着用 `mt` 从驱动器这一侧确认：

```bash
[root@dev-rl-tape mhvtl]# mt -f /dev/nst1 status
SCSI 2 tape drive:
File number=-1, block number=-1, partition=0.
Tape block size 0 bytes. Density code 0x5e (LTO-8).
Soft error count since last status=0
General status bits on (1010000):
 ONLINE IM_REP_EN
```

没有装磁带的驱动器输出会是这样：

```bash
[root@dev-rl-tape mhvtl]# mt -f /dev/nst7 status
SCSI 2 tape drive:
File number=-1, block number=-1, partition=0.
Tape block size 0 bytes. Density code 0x0 (default).
Soft error count since last status=0
General status bits on (50000):
 DR_OPEN IM_REP_EN
```

说明磁带 E01001L8 确实装进了 0 号驱动器。而且驱动器能看出当前支持的 LTO 标准为 `LTO-8` 且状态为 `ONLINE`。

### 写入数据

先造一份测试数据，混入可压缩的全零和不可压缩的随机数据，并记下校验和作为恢复比对的基准：

```bash
[root@dev-rl-tape mhvtl]# cd ~
[root@dev-rl-tape ~]# mkdir -p tape-demo/docs
[root@dev-rl-tape ~]# echo "hello mhvtl virtual tape library" > tape-demo/readme.txt
[root@dev-rl-tape ~]# cp /etc/os-release tape-demo/docs/
[root@dev-rl-tape ~]# head -c 10000000 /dev/urandom > tape-demo/random.bin  # 不可压缩
[root@dev-rl-tape ~]# head -c 10000000 /dev/zero    > tape-demo/zeros.bin   # 高度可压缩
[root@dev-rl-tape ~]# du -sh tape-demo
20M     tape-demo
[root@dev-rl-tape ~]# (cd tape-demo && find ~/tape-demo -type f -exec sha256sum {} \;) > tape-demo.sha256
```

执行写入，为了能够多次使用 tar 连续写入多个文件，这里使用非倒带设备，每个 tar 结束时会落一个 filemark：

```bash
# 首次写入先倒带，确保从头开始写
[root@dev-rl-tape ~]# mt -f /dev/nst1 rewind

# 写入第一个归档：这里是把 tape-demo 目录下的所有文件打包为一个文件后写入磁带
[root@dev-rl-tape ~]# tar cvf /dev/nst1 -C ~ tape-demo
tape-demo/
tape-demo/docs/
tape-demo/docs/os-release
tape-demo/readme.txt
tape-demo/random.bin
tape-demo/zeros.bin

# 查看当前驱动器状态：File number 变为 1 了
[root@dev-rl-tape ~]#  mt -f /dev/nst1 status | sed -n 2p
File number=1, block number=0, partition=0.

# 写入第二个归档：这次只写入 tape-demo 下部分文件
[root@dev-rl-tape ~]# tar cvf /dev/nst1 -C tape-demo readme.txt docs
readme.txt
docs/
docs/os-release

# 再次查看当前驱动器状态：File number 变为 2 了
[root@dev-rl-tape ~]# mt -f /dev/nst1 status | sed -n 2p
File number=2, block number=0, partition=0.
```

现在查看虚拟磁带背后的文件大小：

```bash
[root@dev-rl-tape ~]# du -sh /opt/mhvtl/E01001L8
18M     /opt/mhvtl/E01001L8
```

### 恢复和验证

现在为了验证数据是否一致，重新将磁带中的数据读出：

```bash
[root@dev-rl-tape ~]# mkdir restore
[root@dev-rl-tape ~]# mt -f /dev/nst1 rewind
[root@dev-rl-tape ~]# tar xf /dev/nst1 -C restore
[root@dev-rl-tape ~]# (cd restore && sha256sum -c ~/tape-demo.sha256)
/root/tape-demo/docs/os-release: OK
/root/tape-demo/readme.txt: OK
/root/tape-demo/random.bin: OK
/root/tape-demo/zeros.bin: OK
```

全部 `OK`，包括那份不可压缩的随机数据—，从写入、压缩、落盘到读回、解压、还原，整条链路字节级一致。

### 卸带与持久化

用完磁带后需要把磁带退回槽位（先倒带是好习惯）：

```bash
[root@dev-rl-tape ~]# mt -f /dev/nst1 rewind
[root@dev-rl-tape ~]#  mtx -f /dev/sch0 unload 1 0
Unloading drive 0 into Storage Element 1...done
```

此时，数据永远留在磁带上了，这就达到了数据归档的意义。后续还可以通过邮槽将该磁带从磁带库中取出并永久保存到特定的地方。

## 总结

到这里，一套能装带、备份、定位、恢复的虚拟磁带库就跑通了。mhvtl 的价值也正在于此：它把对磁带库的操作通过软件的形式完整的模拟出来，让开发人员在不依赖物理磁带库的情况下，也可以操作磁带库。而且，这套完整的操作经验在真实的磁带库上一样成立。
